# 體驗打磨：工作規則

寫於 2026-11-13。讀者是 Claude Code。每次開工先把這份從頭讀完，再讀 `docs/11_體驗打磨-清單.md`（進度與發現都記在那裡，第一次開工時由你建立）。

寫這份的人沒有看過 10/19 之後的程式。**repo 的現況以你讀到的為準**；這份文件跟程式對不上時，照程式，並在回報裡講一聲。

## 1. 目的

把 iPLoT 現有的每個功能，提升到「第一次用的人不需要旁人幫忙也能順利用完」的程度。

**這個人是誰**（判斷任何一件事時都想著他）：
- 用 Mac，第一次從瀏覽器下載 iPLoT。
- 不會寫程式，看不懂 traceback，不知道什麼是終端機的錯誤輸出。
- 旁邊沒有人可以問。卡住超過一分鐘就會關掉，而且不會回報。
- 用繁體中文。

**不是目的**：加新功能、重構、讓程式碼更漂亮、提升效能。這一輪只處理「現有功能用起來哪裡會讓這個人卡住或嚇到」。

## 2. 你做不到的事（先講清楚）

你看不到畫面，也沒辦法真的用滑鼠按。所以這份工作是**從程式碼能確定的那部分體驗**：訊息寫了什麼、錯誤有沒有被接住、動作有沒有回應、文件跟程式一不一致。版面好不好看、順不順手，不在你的範圍，不要猜，也不要為了「看起來更好」去改版面。

## 3. 範圍與順序

照新手實際會走的路排。一次做一個區域，做完才做下一個。

| 順序 | 區域 | 包含 |
|---|---|---|
| 1 | 安裝與啟動 | `README.md` 的安裝段、操作說明文件、`iPLoT.command`、`iPLoT.sh`、啟動時的 Python 版本檢查、`main.py` 從啟動到面板出現 |
| 2 | 面板 | 按鈕的產生、按下模組到結果出現、「＋」新增模組、右鍵選單、對話框 |
| 3 | 工作坊 | 清單的取得與顯示、安裝、更新、上傳模組 |
| 4 | 回報與討論 | 送出回報、看討論、沒登入或沒 GitHub 帳號時的表現 |
| 5 | 更新與重新啟動 | `modules/更新/`、核心更新的下載與替換、失敗時的復原 |
| 6 | 行事曆 | `modules/行事曆/` 全部 |
| 7 | 互通與主控面板 | `modules/互通/`、主控面板模組 |
| 8 | 其餘模組 | `modules/` 底下其他已經在 `main` 上的模組，一個一個來 |

第一次開工時，先列出 `modules/` 底下實際有哪些模組，把第 8 區展開成一個模組一列，寫進清單檔。

**不在範圍內**：
- 名字是 `test` 開頭的模組。
- 還沒合併進 `main` 的分支上的東西（例如 Lean 模組）。
- `tests/`、`tools/`、`.github/`、發佈用的腳本。
- 別的 repo（`iplot-workshop`、`iplot-modules`、`reals-game`）。

## 4. 體驗標準

盤點時，對每個區域逐條檢查這十二條。每一條都要能指到具體的檔案與行號，不寫「整體感覺」。

**E1 使用者看不到 traceback。**
任何例外到達使用者眼前之前，都要變成一句人話。完整的 traceback 寫進記錄檔（沿用程式現有的記錄方式；沒有就記為 B 類發現，不要自己發明一套）。
檢查：找所有會把例外內容直接顯示出來的地方，包含 `str(e)`、`repr(e)`、`traceback.format_exc()` 被放進對話框或頁面的情況。

**E2 錯誤訊息有三件事。**
(1) 什麼事沒做成；(2) 知道原因的話，原因是什麼；(3) 現在可以怎麼做。
不出現例外類別的英文名（`FileNotFoundError`、`HTTPError`）。不責怪使用者。不用「發生錯誤」「操作失敗」這種沒內容的句子。
好的例子：「工作坊的清單抓不下來，可能是沒有網路。確認網路後再按一次『重新整理』。」
壞的例子：「錯誤：URLError」「更新失敗」。

**E3 動作有回應。**
按下去之後超過 1 秒才有結果的動作，要立刻有「進行中」的表示。超過 10 秒的，要說大概多久，或是可以取消。
檢查：找所有網路請求、解壓縮、下載、跑子程序的地方，看它是不是在主執行緒上卡住介面、有沒有任何提示。

**E4 空的時候說明原因。**
清單、頁面、面板沒有東西可以顯示時，要說為什麼是空的，以及下一步做什麼。不能是一片空白。

**E5 不能復原的動作先確認。**
刪除、覆寫、發佈、取消公開，動手前要有確認。確認框寫明：會發生什麼、能不能復原。按鈕的字是動作本身（「刪除」「取消」），不是「是」「否」。

**E6 用字一致。**
同一個東西只有一個名字。第一次開工時建立用字表（寫在清單檔最上面）：先讀程式和文件裡現在用的詞，同一個東西出現兩種以上叫法時，選出現次數最多的那個，其他的記為發現。
繁體中文，台灣用語（「資料夾」不是「文件夾」，「設定」不是「設置」，「檔案」不是「文件」）。按鈕用動詞。中文與英文、數字之間不加空格的現有慣例，照現有的，不要全面改。

**E7 第一次打開就知道第一步。**
每個模組第一次打開時，畫面上要看得出第一件事該做什麼，不需要先讀文件。
檢查：模組第一次執行、還沒有任何資料時，顯示什麼。

**E8 網路的三種失敗各有處理。**
沒有網路、連線逾時、對方回錯誤（含 GitHub 的次數限制）。三種都不能讓介面卡死，三種都要有 E2 那樣的訊息。所有網路請求都要有逾時。

**E9 檔案與路徑的常見狀況。**
資料夾不存在、沒有權限、磁碟滿了、路徑裡有空白、中文或特殊字元。這些要嘛正常運作，要嘛有 E2 那樣的訊息。
檢查：找所有組路徑、開檔、寫檔的地方。特別注意把路徑塞進 shell 指令字串的寫法。

**E10 寫使用者的資料不留半個檔。**
寫入使用者資料（行事曆內容、設定、模組的檔案）時，先寫暫存檔再換名。寫到一半失敗，原來的檔案要完好。

**E11 文件與程式一致。**
`README.md` 和操作說明裡給使用者照做的每一步，對著程式核一次：按鈕的名字、選單的位置、跳出來的字、需要的版本。對不上的，改文件（程式沒錯的話）。

**E12 視窗與程序收乾淨。**
視窗的標題看得出是什麼。關掉視窗後不留下還在跑的程序。開出來的新視窗會在最前面（這條只在 macOS 查）。

## 5. 發現的分類

每一個發現都要分到三類之一。**分不出來就當 B。**

### A 類：直接做
- 改訊息的文字（符合 E2、E6）。
- 把顯示給使用者的例外換成人話，traceback 改寫進現有的記錄。
- 補空狀態的說明文字（E4）、第一次使用的提示文字（E7）。
- 替已經存在的破壞性動作補上確認框，或改確認框的字（E5）。
- 替已經存在的網路請求補上逾時與失敗訊息（E8）。
- 替已經存在的慢動作補上「進行中」的文字提示，前提是不需要改執行緒或程序的結構（E3）。
- 路徑的引號與跳脫（E9）。
- 把直接寫檔改成先寫暫存再換名，前提是檔案格式與位置都不變（E10）。
- 改文件讓它跟程式一致（E11）。
- 視窗標題（E12）。
- 替以上任何一項補測試。

A 類的共同條件：**成功的那條路，使用者看到的行為不變**；只有失敗、空的、第一次這三種情況變好。

### B 類：記下來，不要做
- 會改變成功路徑上既有行為的任何修改。
- 改資料的格式、存放位置、檔名。
- 改 `main.py` 裡載入模組、執行模組的邏輯。
- 改 `config.py` 的預設值。
- 改模組與核心之間的約定（`app` 物件上的東西、`iplot.py` 的進入方式）。
- 為了 E3 需要把工作搬到另一個執行緒或程序。
- 新增按鈕、新增選項、新增畫面。
- 拿掉任何現有的功能或按鈕。
- 需要新增記錄機制才能做到的 E1。
- 任何你覺得「應該這樣比較好」但上面 A 類沒有列到的事。

B 類的每一項，在清單檔裡寫清楚：現在的行為、為什麼對新手是問題、你建議的改法、改了會影響什麼。寫到研究助理不用看程式就能決定要不要做。

### C 類：不做，也不用記
- `docs/05_進度與下一步.md` 裡「已知但刻意不處理」那幾節列的每一項。
- Windows、Linux 上的問題。
- 簽章、公證、Gatekeeper。
- 重構、改變數名、搬檔案、整理匯入。
- 升級或新增依賴套件。
- 效能。
- 測試本身的整理。

## 6. 一輪怎麼做

一輪處理一個區域。照這個順序，不要跳步。

**步驟 1：定位。** 讀清單檔，找第一個狀態不是「完成」的區域。

**步驟 2：盤點。** 把那個區域的程式讀完（讀完整的檔案，不要只搜尋關鍵字）。對 E1 到 E12 逐條檢查。每個發現寫成一列：

```
編號｜檔案:行號｜現在的行為｜違反哪一條｜建議的改法｜分類
```

盤點階段不改任何程式。盤點完，先把這個區域的發現全部寫進清單檔並 commit（訊息：`docs: 體驗打磨 盤點 <區域名>`），再開始修。

**步驟 3：修 A 類。** 一個發現一個 commit。每一個照這個順序：
1. 先寫一個會失敗的測試，釘住修好之後的行為。測試裡有副作用的呼叫（網路、刪檔、開視窗）先擋掉。
2. 改程式到測試通過。
3. 跑完整的測試（照 repo 現有的跑法，兩種都跑）與 ruff。全綠才 commit。
4. commit 訊息：`fix(<區域>): <一句話講使用者會看到什麼不同>（體驗 <編號>）`。
5. 在清單檔把那一列標成「已修」並寫上 commit 的短 hash。

純文字的修改如果真的沒辦法測（例如文件），可以不寫測試，在清單檔那一列註明「無測試：原因」。

**步驟 4：模組的變更紀錄。** 改到的模組如果有 `CHANGELOG.md`，在最上面加一段「未發佈」，一行一項，用使用者看得懂的話寫。不要改版本號。

**步驟 5：收尾。** 區域裡的 A 類全部處理完，把清單檔裡那個區域的狀態改成「完成」，寫一段小結（格式見第 9 節），commit。然後直接回到步驟 1 做下一個區域。

## 7. 界線

**只在 `polish/ux` 分支上工作。** 第一次開工時從最新的 `main` 開出來。

絕對不要做：
- 不 push 到 `main`，不合併，不開 PR。可以 push `polish/ux` 分支本身當備份。
- 不打 tag，不改任何版本號，不跑發佈的腳本，不碰線上的 `update.json`、`index.json`。
- 不改別的 repo。
- 不讀、不寫、不刪使用者真實的資料（例如 `~/Documents/行事曆`、`~/iPLoT`）。測試一律用暫存資料夾。
- 不安裝任何套件，不升級任何東西。
- 不執行會跳出視窗等人按的程式。
- 暫存資料夾開在 repo 裡被 `.gitignore` 忽略的位置，不要開在外接碟最上層；用完刪掉並確認刪掉了。
- 不跑 `lean`、`lake`、`elan`。
- 不改這份文件。覺得這份文件哪裡不對，寫進回報。

## 8. 什麼時候停下來

碰到下面任何一種，停下來回報，不要自己想辦法繞：

1. **測試紅了，試了兩次修不好。** 把那個 commit 還原，那一項改記為 B 類並寫明原因，然後繼續下一項。同一個區域發生三次，整個停下來。
2. **發現會弄丟使用者資料、或把不該公開的東西公開出去的問題。** 不管它算哪一類，立刻寫進清單檔最上面的「最優先」區，然後停下來回報。這類問題不要自己修。
3. **開工時 `main` 上的測試本來就是紅的。** 不要開始，直接回報。
4. **工作樹不乾淨、或 `polish/ux` 上有不是你做的 commit。** 不要動，回報。
5. **全部區域都完成了。**

碰到 B 類發現**不用停**，記下來繼續做。

## 9. 清單檔與回報的格式

`docs/11_體驗打磨-清單.md` 的結構：

```
# 體驗打磨清單

## 最優先（資料遺失或隱私）
（沒有就寫「無」）

## 用字表
| 東西 | 用這個詞 | 不要用 |

## 進度
| 順序 | 區域 | 狀態（未開始／盤點中／修正中／完成） | A 已修／A 總數 | B 數 |

## 等研究助理決定（B 類）
| 編號 | 區域 | 現在的行為 | 為什麼是問題 | 建議的改法 | 改了會影響什麼 |

## 各區域的發現
### 1 安裝與啟動
| 編號 | 檔案:行號 | 現在的行為 | 違反 | 建議的改法 | 分類 | 狀態 |

（小結）
```

編號用「區域序號-流水號」，例如 `3-07`。

每個區域的小結，以及每次停下來時的回報，都寫這五件事，每件一兩行：
1. 這個區域盤到幾個發現，A、B 各幾個，A 修了幾個。
2. 新手最會卡住的那一個是什麼，修了沒。
3. 哪些 A 類沒修成，為什麼。
4. 偏離這份文件的地方與理由。沒有就寫「無」。
5. 測試數與 ruff 的結果。

回報裡的每一個數字，寫之前對著 repo 再核一次。
