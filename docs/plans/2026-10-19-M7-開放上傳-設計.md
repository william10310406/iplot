# M7 開放上傳：誰都能把自己的模組放上工作坊（設計）

2026-10-19。這份是設計（規格），不是工作單。方向是研究助理在 2026-10-19 的對話裡定的：任何人都能上傳自己的模組；審查不是這一版的事，由另一位同事處理；上傳走 GitHub（上傳的人要有 GitHub 帳號）。細節（D100–D109）是這份提的，研究助理看過再定；定了之後 Claude Code 依這份寫工作單（`docs/plans/2026-10-19-M7-開放上傳.md`）再實作。
前提：核心是 0.5.1。**這個里程碑核心邏輯一行都不改**（D80）。動到的是隨附模組「工作坊」、`config.py`、`tools/publish.py`，另外多一個公開 repo `iplot-modules` 與它的機器人。
參考：`docs/07` 第 6、7、11 節；D54、D69、D70、D71、D73、D74、D77、D78、D79、D80。

## 0. 一句話

有 GitHub 帳號的人，把模組資料夾壓成 zip，在 `iplot-modules` 的「上傳模組」表單拖進去、送出；機器人只做機械檢查——zip 的形狀、名字是誰的——過了就放進 repo、重產清單、更新網站，在 issue 回一句。iPLoT 的工作坊照舊讀一份 `index.json`，每一列多一行「上傳者」。核心的更新（`update.json`）留在只有研究助理能寫的 `iplot-workshop`，上傳碰不到。審查這一版不做，位置留好（第 8 節）。

## 1. 需求

來源：研究助理（2026-10-19）：「我想要的是任何人都能更新工作坊，就是所有人都可以寫自己的模組並且上傳，審查的話目前不是我要解決的事情，會是我的另一個同事去思考解決這類問題的辦法」。比較過自己架收檔的伺服器之後，定「還是以 GitHub」。

- **R1 誰都能上傳**：有 GitHub 帳號就能把自己寫的模組放上工作坊，不用經過研究助理。
- **R2 名字有主人**：上傳的人能更新自己的模組；別人不能用同一個名字蓋掉。
- **R3 碰不到核心**：開放上傳不能讓任何人換掉別人的核心。
- **R4 只用瀏覽器**：上傳不用 git、fork、PR；在 Finder 壓縮、在網頁拖進去。
- **R5 審查留位置**：同事之後接上，不用改上傳方式、不用改清單格式、不用再換一次 iPLoT 這邊的東西。
- **R6 核心不改**（D80）。
- **R7 看得到是誰傳的**：清單上每個模組都標上傳者。

**做好的樣子：**
- 上傳的人：在 Finder 對著模組資料夾按右鍵「壓縮」→ 打開 `iplot-modules` 的「上傳模組」表單 → 把 zip 拖進去、勾「我知道…」、送出 → 一兩分鐘後 issue 裡出現「收到了：「整理桌面」0.0.1，5 個檔…」，issue 關掉 → 再過幾分鐘，任何人在 iPLoT 按「工作坊」，清單上就有「整理桌面」，底下一行「上傳者：@xxx」。
- 傳錯的人：issue 裡一句話說哪裡不對（例如「zip 裡要剛好是一個資料夾…」），issue 關掉；改好再開一個。
- 用 iPLoT 的人：清單最上面多一行「這裡的模組是大家上傳的，沒有人審查…」，每一列多一行上傳者；安裝、更新、覆蓋、第一次執行前問一次，都跟現在一樣。

## 4. 上傳表單

`.github/ISSUE_TEMPLATE/上傳模組.yml`（issue form）：

- `name: 上傳模組`，`title: "上傳："`，`labels: [上傳]`。
- `upload`（id `zip`）：標籤「模組的 zip」；說明「在 Finder 對著模組的資料夾按右鍵 →「壓縮」，把壓出來的 .zip 拖進來。一次一個模組。zip 裡的每個檔都會公開，包括 Finder 裡看不到的（按 ⌘⇧. 顯示）：`.venv`、`.history` 和模組自己存的資料。表單說檔案太大，多半是這些：先複製一份資料夾、拿掉它們再壓。」；`validations: { required: true, accept: ".zip" }`。表單的 `upload` 欄位收 .zip，上限 25 MB。
- `textarea`（id `notes`）：「這一版改了什麼（選填）」；說明「模組裡有 CHANGELOG.md 的話以它為準，這裡不用寫。」
- `checkboxes`（id `agree`，必勾）：「我知道上傳的東西誰都看得到、誰都能下載執行；這個名字之後只有我的帳號能更新。」
- `config.yml`：`blank_issues_enabled: false`。沒有寫入權限的人開 issue，只有表單可以選。

機器人的略過清單要等下載之後才用得上：表單的 25 MB 擋在前面，帶 `.venv` 的模組根本送不出去（「科學計算」照 Finder 壓是 169 MB），畫面上只有 GitHub 的錯誤。比較小的就整包公開，例如「互通」的 `.python`、`.patched`（本機的絕對路徑）、「科學計算」的 `HKn/<學生>/`（學生的名字與作業）。0.5.1 為了這件事才讓 `publish.py` 只收 git 追蹤的檔；Finder 壓縮又把這個洞打開了。M7b 的「上傳」打包時預設排除這類本機狀態（第 12 節）。

送出之後內文長什麼樣（附件的網址格式、欄位的標題）文件沒寫，Task 0 先看（第 14 節）。

## 5. 機器人

### 5.1 什麼時候跑

- 觸發：`issues: [opened]`、`push`（`main`）、`workflow_dispatch`、`schedule`（每小時一次）。`schedule` 只當掃尾：一次沒收完的（最多 30 份）、連不上而沒收成的，一小時內會再收。公開 repo 60 天沒動靜 GitHub 會停掉它，那時本來也沒有東西要掃。
- `concurrency: { group: modules, queue: max }`：一次只跑一個，其他排隊，最多 100 個。不寫 `queue: max` 的話，GitHub 只留一個在排隊，新來的會把排隊中的那一個取消。
- receive 每次都處理**所有**還開著、帶「上傳」標籤、沒有「已發佈」「沒收」「卡住」標籤的 issue，舊的先。所以某一次被取消、失敗了，下一次（下一份上傳、研究助理 push、手動跑）照樣收。標籤沒貼上的情況見第 14 節。
- **收過沒有，認 `received.json`，不認 issue 開著還是關著。** repo 根目錄的 `received.json`（`{issue 編號: {"name", "version", "owner_id", "at"}}`）跟模組寫在同一個 commit，跟 push 一起成功或一起失敗。開著的 issue 編號已經在裡面（push 成功了、回覆或關 issue 沒做成），就只補回覆、標籤、關 issue，不再收一次。不然沒有 CHANGELOG 的會再發一版，有的會被回「版本沒有比較新」。不用 `git log --grep`：checkout 預設是淺 clone，只看得到最新的 commit。
- receive 每次順便確認四個標籤在（「上傳」「已發佈」「沒收」「卡住」），不在就建：表單的 `labels` 只會貼 repo 裡已經有的標籤。所以 repo 建好之後要先跑一次（第一個 commit 的 push 就會跑）。
- 每一次跑都 build＋deploy，不管 receive 收進了東西沒有、成功了沒有。D106 讓內容沒變時 zip 的 sha256 不變，多部署一次沒有副作用；Pages 每小時 10 次的軟上限不適用於自己寫的 Actions workflow。只在收進東西時才 build 的話，部署失敗（Pages 超過 10 分鐘、網站超過 1 GB、build.py 自己的錯）之後就沒有人重試，上傳的人卻已經收到「收到了」。build、deploy 的 `if` 都帶 `!cancelled()`：GitHub 預設前一個 job 失敗或被跳過，後面的全部跳過。
- receive 用 `GITHUB_TOKEN` push，不會再觸發一次 workflow（GitHub 的規矩），所以 build、deploy 跟在同一次裡面做。
- receive 與 build 的 checkout 都指定 `ref: main`：`issues` 事件預設拿到的 commit 是事件發生那一刻的，看不到前一次 receive 剛推上去的。

### 5.2 一份上傳怎麼收

照順序；哪一步不過就停在那裡、回那一句（第 10 節）。

**每一份各自處理，一份出錯不擋別人。** 從打開 zip（`ZipFile()` 本身就會丟例外）到 `git add`，每一份包在自己的 `try` 裡：
- 已知的例外——`BadZipFile`、`RuntimeError`（加密）、`NotImplementedError`（壓縮法不支援）、`zlib.error`、`EOFError`、`ValueError`、`UnicodeDecodeError`、`OSError`——回第 10 節「zip 打不開或壞了」那一句，貼「沒收」、關掉。
- 其他任何例外（接 `Exception`，含 `MemoryError`、`RecursionError`）——回「機器人處理不了這份上傳，研究助理會看」，貼「卡住」、拿掉「上傳」，issue 留著。它就不會再排進下一次。
- 全部檢查都過了才寫進工作目錄；寫到一半出錯，`git reset --hard` 加 `git clean -ffdx -- modules/<名稱>/` 回到這一份之前，再接著處理下一份。

不這樣做的話：receive 每次都從最舊的收起，一份讓它丟例外的上傳（用任何壓縮軟體加個密碼就做得到）永遠排第一，之後誰的都收不進來，直到研究助理手動關掉它。

1. 上傳的人是一般帳號（`issue.user.type == "User"`），而且不是 `ghost`：帳號在機器人處理之前刪掉（或轉成組織），issue 會改掛到 `ghost` 這個共用的佔位帳號，type 照樣是 User。名字記到它的 id 底下的話，之後任何刪了帳號的人都能更新它。`ghost` 的 id 在 Task 0 記下來；registry 永遠不存它。
2. 「模組的 zip」那一節裡剛好一個 `.zip` 附件，網址完全符合 Task 0 看到的附件前綴（例如 `https://github.com/user-attachments/files/<數字>/<檔名>.zip`）。只要求在 `https://github.com/` 底下不夠：別的 repo 的檔、release 都在那底下，審查要用的「附件網址」就不一定是這個 issue 傳的。
3. 下載：總共 60 秒（自己用 `time.monotonic` 算；`urlopen(timeout=…)` 是每一次讀的上限，一個位元組一個位元組慢慢送就永遠不會逾時），超過 25 MB 就停。轉址自己處理：只跟 `https`、只跟 Task 0 記下的 GitHub 的 host。不帶 token（公開 repo 的附件不用登入）；Task 0 不通才帶，而且只帶給第一個 host：Python 的 `urllib` 轉址時把 `Authorization` 原樣帶到下一個 host（2026-10-19 實驗過），這個 token 有 `contents: write`。
4. 打開 zip。不用 `extractall`，一條一條看過才讀：
   - **略過**（回覆裡列出來）：`__MACOSX/`、`._` 開頭的檔（Finder 壓縮附帶的）；各台電腦自己的名字 `.history`、`.origin`、`.unconfirmed`、`__pycache__`、`.DS_Store`（不分大小寫，跟 `tools/publish.py`、`workshop.py` 的 `SKIP` 同一組）；任何一段 casefold 之後以 `.git` 開頭的（`.git`、`.gitignore`、`.gitattributes`、`.gitmodules`，檔、資料夾都算；`.github`、`.gitkeep` 也會被略過，回覆裡說一聲）、`.venv/`；名稱剛好是 `Icon\r` 的檔（Finder 的資料夾自訂圖示，結尾是 CR；照控制字元的規則整份會被退）；符號連結（`stat.S_ISLNK(info.external_attr >> 16)`；Finder 會原樣帶上，內容是連結目標的字串）。上傳的 `.gitignore` 會讓 `git add` 悄悄少收檔，`.gitattributes` 會改掉位元組（`eol`）或讓 `git add` 失敗（`working-tree-encoding`），子資料夾裡一個叫 `.git` 的檔會讓整個資料夾變成子模組指標（2026-10-19 實驗過）。
   - 剩下的：剛好一個最上層資料夾 `<名稱>/`，裡面有 `iplot.py`（檔名剛好是小寫；`iPLoT.py` 不算，跟 `core/scan.is_module`、`workshop.install` 一樣）。
   - 每一條路徑（NFC 正規化之後）：不能有 `..`、不能是絕對路徑、不能有反斜線與控制字元、不能有 Windows 不能用的字元（`:*?"<>|`）、不能是保留字（CON、NUL…），每一段結尾不能是 `.` 或空白；除了目錄條目結尾的那個 `/`，任何一段都不能是空的（`m//iplot.py` 寫到磁碟上就是 `m/iplot.py`，後寫的蓋掉先寫的）。
   - 重複與衝突一次檢查完：每一條拆成段、每一段 NFC＋casefold，連同所有上一層（隱含的資料夾）一起算。一個檔剛好是別條的上一層（`a/b` 與 `a/b/c`）、目錄條目跟檔同名、同一組段出現兩次（含只差大小寫；也含隱含的資料夾只差大小寫：`m/A/x` 與 `m/a/y` 在 macOS、Windows 上是同一個資料夾）——都不收。照字串比擋不到這幾種，寫檔時才丟 `FileExistsError`、`IsADirectoryError`。
   - 不能有 `git~<數字>` 這種段（不分大小寫）：Linux 上的 git 也擋 Windows 的短名，`git add` 會失敗。
   - 檔名一律照 UTF-8 解：用 `zipfile.ZipFile(f, metadata_encoding="utf-8")` 打開（3.11 起有；只作用在沒標 UTF-8 旗標的條目）。Finder 的「壓縮」寫的檔名是 UTF-8，卻**不標**旗標（2026-10-19 用 `ditto -c -k --sequesterRsrc --keepParent` 驗過：每一條的 `flag_bits` 都沒有 0x800，Python 預設照 cp437 解成亂碼）。解不開（例如舊的 Windows 內建壓縮寫的 Big5）在打開時就丟 `UnicodeDecodeError`：不收，說一句。不要用「解出來的名字有沒有中文」判斷：沒解對的時候名字裡一個中文字都沒有，亂碼的名字照樣過得了名稱規則。
   - 解完每一條路徑做 NFC：ditto 照磁碟上的寫法放，可能是 NFD。
   - zip 的條目（略過之前）≤ 20000：`ZipFile` 打開之後先看 `len(infolist())`，還沒讀任何內容；超過回「zip 裡的條目太多」。下面的 2000 個檔算略過之後的：Finder 的 `._` 讓每個檔算兩次，帶 `.venv` 的正常模組原始條目就有 2146 條。
   - 解開合計 ≤ 100 MB、≤ 2000 個檔。讀任何內容之前，先把沒略過的條目的 `file_size` 加總：Python 的 `zipfile` 吐出來的不會超過 `file_size`，所以這就是上限，擋得住 zip 炸彈。每一條用 `z.open(info)` 一次讀 64 KB，讀完實際的位元組數要等於 `file_size`：宣告的比實際小，Python 丟 `BadZipFile`（CRC）；比實際大，Python 不報錯——兩種都回「這個 zip 打不開或壞了」。不用 `z.read(info)` 一次整條讀進記憶體。
5. 名稱跟核心的 ＋ 同一套規則（`core/create.py` 的 `_bad_name`，D54），再加機器人自己的兩條（只管上傳，核心不改）：
   - 名稱裡不能有看不見的字：Unicode 的 Default_Ignorable_Code_Point（零寬、方向控制、BOM、變體選擇符、韓文填充字…，表從 `DerivedCoreProperties.txt` 抄進機器人）、ASCII 空白以外的空白（NBSP、全形空白、點字空白）、類別 Co、Cn；頭尾不能是空白。同一個名字裡，拉丁字母不能跟西里爾、希臘字母混用（用 `unicodedata.name` 開頭的 LATIN／CYRILLIC／GREEK 判斷）。
   - 不能「太像」：拿掉空白、NFKC、casefold 之後，跟 registry 裡別人的、保留的、種子的任何一個一樣，就不收。
   不然「開工」後面加一個零寬空格、「開Ｔｅｒｍｉｎａｌ」、「更新」加全形空白，核心都收、鍵也不同，在用的人的 Mac 上是另一個資料夾，清單上、面板上卻看起來一模一樣（2026-10-19 實驗過十幾種寫法）。
6. 名字是誰的（第 6 節）。再看兩個上限（數字在第 13 節）：這個帳號 24 小時內收下的份數、名下的名字數（都從 `received.json`、`registry.json` 數）；第一次上傳的話，`modules/` 現在的大小加上這一份不能超過門檻。不然一個帳號用 41 個名字各傳一個 25 MB，網站就超過 GitHub Pages 的 1 GB，整個工作坊停掉。這要在 receive 擋：到 build 的時候已經 push、已經回「收到了」。
7. `iplot.py` ≤ 1 MB、照核心的 `meta.read_meta` 讀一次（跟 core 同一份抄本：`utf-8-sig` 解碼、`ast.parse`、docstring 第一段、`ICON`、`TITLE`），外面再包一層 `try`。`meta.error` 有行號的回「語法錯誤」；沒有行號的（不是 UTF-8、有 NUL）回「iplot.py 不是 UTF-8」；`MemoryError`、`RecursionError` 回「iplot.py 解析不了（太複雜）」——100 KB 的一串 `-` 就會讓 `ast.parse` 丟 `MemoryError`，`read_meta` 不接它，iPLoT 掃描時也會碰到。不要把位元組直接給 `ast.parse`：它照檔頭的 coding 宣告解碼，機器人過了，iPLoT（`utf-8-sig`）卻讀不了。有語法錯誤不收：傳上來，別人裝了也跑不起來。說明 ≤ 500 字、`ICON` ≤ 16 字；超過的截短加「…」，回覆裡說一聲。
   有 `TITLE` 的話，`TITLE` 也走第 5、6 步：它的鍵要是自己的名稱，或沒有人登記、不是保留的、不太像別人的。面板的格子與第一次執行前那一句用的是 `TITLE`（`core/scan.py:44`、`core/core.py:113`），只看資料夾名的話，叫「隨便取」的模組寫 `TITLE = "更新"`、`ICON = "⬆️"`，裝了就多一格跟隨附的一模一樣的「更新」。
8. 版本與 notes（第 7 節）。notes ≤ 1000 字，超過的一樣截短；`registry.json` 只存截短之後的。沒有上限的話，一份 60 MB 的 CHANGELOG 第一段壓起來只有一百多 KB：`index.json` 就是 60 MB，每個人按「工作坊」都要下載；兩份讓 `registry.json` 超過 GitHub 的 100 MiB，之後每一次 push 都被拒。build 再擋一次：`index.json` 超過 2 MB 就讓 job 失敗、不部署。
9. `may_publish(upload)`：這一版一律回「可以」（第 8 節）。
10. 寫進去：`modules/<名稱>/` 整個換成這一次的檔；`registry.json` 那一筆只改機器人的那幾欄（第 6 節）；commit，訊息「上傳：<名稱> <版本>（@<帳號>，#<issue>）」，加一行 `Co-authored-by` 掛上傳的人。`git add -f -- modules/<名稱> registry.json received.json`（不用 `-A`）；commit 之前用 `git ls-files -s` 核對：`modules/<名稱>/` 底下每一筆都是 100644，路徑與 blob 都跟收下的檔用 `git hash-object --no-filters` 算的一樣，沒有 160000。不一樣就還原這一份，回「這份 zip 寫不進 repo」。

**每收一份就 commit、push 一次**；同一次裡，後一份用前一份寫完之後的 registry 判斷。**push 成功才回覆、貼標籤、關 issue。** push 不成功分三種：
- 落後（研究助理剛好也 push 了）：不 rebase。`git reset --hard origin/main`，這一份不回覆、issue 留著，這一次就停。研究助理的 push 本身會排一次 run（`queue: max`，先來先跑），那一次用新的 registry 從頭收。rebase 會出事（2026-10-19 實驗過兩種）：衝突時停在一半，`registry.json` 是壞的 JSON；沒衝突時把用舊 registry 做的決定合上去——研究助理剛把名字轉給別人、或剛設成保留，舊主人的新版照樣推上去，`registry.json` 還可能出現重複的鍵。
- 被擋（例如 GitHub 的 push protection 在檔案裡找到金鑰）：這一份算沒收，`git reset --hard origin/main`，回第 10 節「push 被擋」那一句，接著收下一份。
- 連不上（網路、5xx）：reset，這一次就停，回第 10 節「push 不成功」那一句，issue 留著。
- 每個 git 指令都看結束碼。讀 `registry.json` 用 `object_pairs_hook` 擋重複的鍵。

### 5.3 回覆

- 收到：「收到了：「<名稱>」<版本>，<N> 個檔。網站更新之後（通常幾分鐘）在 iPLoT 按「工作坊」就看得到；超過一小時還沒有，在這裡留言。」＋公開的檔、略過的檔（各一個程式碼區塊）。標籤「已發佈」，關掉。
- 沒收：第 10 節那一句。標籤「沒收」，關掉；改好之後開一個新的。
- 名稱、帳號名、檔名一律放在程式碼裡：不會變成連結、不會 @ 到人。名稱可以是 `@someone`、`#1`（核心的規則收）。行內用反引號包，反引號的數目比內容裡最長的那一串多一個；程式碼區塊列完整路徑（`<名稱>/…`），圍欄長度 = max(3, 內容裡最長的反引號串＋1)。
- 回覆不能太長：略過的照群組算數量（「`.venv/` 2144 個」「`__MACOSX/` 19 個」），公開的檔最多列 200 條，後面寫「還有 N 個」，整則壓在 20,000 字以內。一份帶 `.venv` 的正常模組，逐條列略過的就要 18 萬字。
- 回覆送不出去就改送短版（只有「收到了：<名稱> <版本>，<N> 個檔」）；貼標籤與關 issue 跟回覆分開做，一個失敗不影響另一個。
- 寫 GitHub 一次一個，中間隔 1 秒；貼標籤與關 issue 合成一個 `PATCH /issues/{n}`（`labels`、`state`、`state_reason` 一起給），一份上傳只寫兩次（留言＋PATCH）。GitHub 每分鐘最多 80 次、每小時 500 次會產生內容的請求，`GITHUB_TOKEN` 每小時 1000 次。碰到 403／429 照 `retry-after` 等；要等超過 60 秒就停下這一次，剩下的 issue 不碰、不留言，留給下一次，job 不算失敗。一次最多收 30 份，剩下的下一次再收。

### 5.4 規矩

- **只讀不執行。** 上傳的東西只會被解壓、`ast.parse`、寫進 repo，一行都不會被執行——跟收作業一樣（`docs/07` 第 7 節「科學計算」那一段）。
- **issue 的字不進 shell。** workflow 的 `run:` 裡不寫 `${{ github.event.issue.* }}`；腳本從 API 讀 issue，當資料。
- **最少權限。** workflow 頂層 `permissions: {}`；receive 只有 `contents: write`、`issues: write`；build 只有 `contents: read`；deploy 只有 `pages: write`、`id-token: write`。這個 token 屬於 `iplot-modules`，碰不到 `iplot-workshop`。
- **不用第三方 action**；GitHub 自己的 action 釘 commit sha。
- **不用 `pull_request_target`。** 有人開 PR（例如改機器人），只跑測試（`pull_request`，唯讀），不合併、不部署；合不合併是研究助理的事。唯讀不等於碰不到機器人：`pull_request` 跑的是 PR 自己帶的 workflow 檔，concurrency group 整個 repo 共用，PR 加一個 `concurrency: { group: modules, cancel-in-progress: true }` 就能取消正在跑的 receive，或用跑 6 小時的 job 把佇列佔住。所以 fork 的 PR 一律要核可（第 13 節）；核可之前先看 PR 有沒有動 `.github/`，有就不核可。
- 機器人只用標準庫（`urllib`、`zipfile`、`ast`、`json`）；呼叫 GitHub API 用 `urllib` 帶 `GH_TOKEN`。下載附件不用呼叫 API 的那個函式（那個會帶 token）。

### 5.5 workflow 的樣子（示意）

```yaml
name: 收模組
on:
  issues: { types: [opened] }
  push: { branches: [main] }
  workflow_dispatch:
  schedule: [{ cron: "17 * * * *" }]
permissions: {}
concurrency: { group: modules, queue: max }
jobs:
  receive:
    runs-on: ubuntu-latest
    timeout-minutes: 30
    permissions: { contents: write, issues: write }
    steps:
      - uses: actions/checkout@<sha>       # with: { ref: main }
      - uses: actions/setup-python@<sha>   # with: { python-version: "3.12" }
      - run: python -I tools/receive.py
        env: { GH_TOKEN: "${{ github.token }}" }
  build:
    needs: receive
    if: ${{ !cancelled() }}
    runs-on: ubuntu-latest
    timeout-minutes: 10
    permissions: { contents: read }
    steps:
      - uses: actions/checkout@<sha>       # with: { ref: main }
      - uses: actions/setup-python@<sha>   # with: { python-version: "3.12" }
      - run: python -I tools/build.py site
        env: { GH_TOKEN: "${{ github.token }}" }
      - uses: actions/upload-pages-artifact@<sha>   # with: { path: site }
  deploy:
    needs: build
    if: ${{ !cancelled() && needs.build.result == 'success' }}
    runs-on: ubuntu-latest
    timeout-minutes: 10
    permissions: { pages: write, id-token: write }
    environment: { name: github-pages }
    steps:
      - uses: actions/deploy-pages@<sha>
```

### 5.6 build 的規矩

- **照 `registry.json`，不照資料夾。** 只發有 `version`、沒有 `reserved`、沒有 `removed`、`modules/<名稱>/` 在、裡面有 `iplot.py` 的那幾筆；registry 沒登記的資料夾不發。保留、種子那幾筆缺 `version`、`zip_url`，倒進 `index.json` 的話，`read_index` 對整份丟 `ValueError`，所有人（包括 0.5.1）的工作坊都打不開。
- **一筆一筆各自 `try`。** 讀不了、打不了的那一筆跳過，寫進 Actions 的 summary；其他照發。第一天就會有「registry 有、資料夾沒有」：開Terminal、重新啟動登記了卻不傳。只有 `index.json`、`index.html` 寫不出來才算整個失敗。
- **寫完自己驗一次。** 用 `workshop.py` 那一份 `read_index` 的副本讀 `index.json`；每個 zip 照 `workshop.install` 要的形狀檢查（最上層 `<名稱>/`、有 `iplot.py`）。不過就讓 job 失敗、不部署。
- **上傳者用現在的帳號名。** build 對每個不同的 `owner_id` 呼叫一次 `GET /user/{owner_id}`，寫進 `index.json` 的 `author`；查不到（逾時、5xx）就用 registry 的 `owner`，不讓 build 失敗；404 寫「帳號已刪除」。帳號改名之後舊名字誰都能註冊（刪除之後 90 天也是）：只用上傳時記的 `owner` 的話，新註冊的人上傳的模組，清單上的上傳者跟原本那位一模一樣。build 的 job 要 `GH_TOKEN`（`contents: read` 就夠）。
- **`zip_url` 照 `tools/publish.py` 的 `_url` 組**：base 之後每一段都 `urllib.parse.quote`；`index.html` 的連結用同一個網址再 `html.escape`。名稱可以有 `#`、`%`（核心的規則收），照原樣接的話，`C#工具` 下載到的是 `模組/C`、`a%20b` 下載到的是 `a b.zip`（`workshop._open` 把 `#`、`%` 當安全字元留著）：「收到了」，卻沒有人裝得起來。

## 6. 名字是誰的：`registry.json`

```json
{
  "整理桌面": {"name": "整理桌面", "owner_id": 87654321, "owner": "someone", "version": "0.0.2",
               "notes": "多了一個資料夾", "issue": 12, "updated": "2026-10-21"},
  "作業系統": {"name": "作業系統", "reserved": true}
}
```

- **鍵**是 NFC 正規化再 casefold 的名稱：macOS 的檔名不分大小寫，相容表意字跟本字是同一個（跟 `workshop._bundled` 同一套）。
- 判斷照這個順序，前面的先：
  1. `reserved: true` → 誰都不收：作業系統、更新、工作坊（工作坊本來就不覆蓋它們，D74）。
  2. `removed: true` → 誰都不收，原主人也不收，直到研究助理拿掉 `removed`。不然原主人再傳一次就算「更新」，下架就撤銷了。
  3. 沒有這個鍵 → 第一次上傳，名字歸上傳的人。記**數字 id**（帳號改名也認得）；`owner` 只是顯示用，每次上傳更新。
  4. 有、`owner_id` 不一樣 → 不收。
  5. 有、`owner_id` 一樣，大小寫跟第一次不一樣（`name` 欄）→ 不收：在分大小寫的系統（Linux）上會變成兩個資料夾。Unicode 的寫法不會不一樣：名稱就是 zip 最上層資料夾名 NFC 之後的字串，寫檔、存 `name`、比對、`index.json` 的 `name`、zip 的最上層都用這一個（`workshop.install` 照字串比 `<名稱>/`，兩邊差一點就裝不進去）。
  6. 有、`owner_id` 一樣 → 更新。
- 三種筆的樣子：保留 `{name, reserved}`；種子 `{name, owner_id, owner}`（還沒傳，沒有 `version`）；一般的 `{name, owner_id, owner, version, notes, issue, updated}`。研究助理手動加的欄（`removed`、`warning`，以後審查加的）可以出現在任何一筆。
- 機器人只寫這幾欄：第一次寫 `name`、`owner_id`；每次寫 `owner`、`version`、`notes`、`issue`、`updated`。其他欄一律原樣留著：整筆重寫的話，被標了 `warning` 的人再傳一版，紅字就不見了。有 `warning` 的照樣能更新，`warning` 留著。
- **種子先登記**給研究助理的帳號：開工、打開核心原始碼、開Terminal、重新啟動、互通、主控面板、行事曆、科學計算、上傳（M7b，D109）。不登記的話，別人可以傳一個「重新啟動」：在用的人那裡它是「版本未知」，按了「覆蓋」，隨附的就換成他的。「上傳」也一樣：M7b 發之前誰都能先傳一個，版本寫 9.0.0，裝了他那一份的人永遠看不到研究助理的 0.1.0 是「可更新」。`registry.json`（含保留與種子）跟表單、workflow 在同一個 commit 上去：早一個 commit 的話，那段時間種子的名字也搶得到。
- **下架**（研究助理手動）：刪掉 `modules/<名稱>/`，那一筆加 `"removed": true`（名字還是原來的人的，不能馬上被搶），push。只擋新的安裝，已經裝了的不會被拿掉。
- **轉名字、救帳號**（例如原主人的帳號刪了）：研究助理改 `owner_id`，push。

## 7. 版本與「這一版改了什麼」

- **模組裡有 `CHANGELOG.md`**：照 D78（`publish.latest`）讀最上面那一節，版本只認數字與點，而且要比 `registry.json` 裡現在的版本新，不然不收——一樣的版本，裝過的人永遠看不到「可更新」。notes 取那一節第一段；表單那一格不用（回覆裡說一聲）。
- **沒有**：版本自動往上加。第一次 `0.0.1`；之後把現在的版本最後一段加一（`0.1.1` → `0.1.2`）。notes 取表單那一格，沒寫就是空的。
- registry 那一筆沒有 `version`（種子先登記的，或研究助理轉過來、還沒傳的）就當第一次：有 `CHANGELOG.md` 照它的版本、不用比；沒有就 `0.0.1`。
- 兩條都只產生工作坊比得了的版本（`workshop._newer` 只比數字）。寫法：`re.fullmatch(r"[0-9]{1,9}(\.[0-9]{1,9}){0,9}", v, re.ASCII)`，不過就回「版本不是 1.2.0 這種寫法」：`publish.latest` 的 `\d` 收全形與別的文字的數字，太長的數字 `_newer` 轉不了 int、回 False。「比較新」跟 `_newer` 同一個比法：每段轉 int 的 tuple，越大越新（`1.1` 之後傳 `1.01` 不收）。

## 8. 留給審查的位置

同事的辦法之後接上。這一版先把接口留好，預設不作用：

1. **`receive.py` 的 `may_publish(upload) -> (bool, str)`**：這一版一律 `(True, "")`。要改成「先審再發」，改這一個函式就好——例如回 `(False, "等審查")`、貼「待審」標籤、issue 留著——表單、`registry.json`、`index.json` 都不動。
2. **`index.json` 頂層的 `notice`**（字串）：工作坊清單最上面那一行。放在 repo 根目錄的 `notice.txt`，build 照抄進 `index.json`；改字就換，iPLoT 這邊不用動。不放 `registry.json` 的頂層：那裡的鍵是模組名稱，有人傳一個叫 notice 的模組就撞上。`notice.txt` 讀不到或是空的，build 就讓 job 失敗、不部署：清單最上面那一行不能無聲地消失。這一版是：「這裡的模組是大家上傳的，沒有人審查。裝進來的模組第一次執行前 iPLoT 會先問；按確定之前，在面板上右鍵「打開程式碼」看一眼。」
3. **每一筆的 `warning`**（字串）：有的話，那一列用紅字多一行。給「被檢舉、還在查」這類狀況。這一版機器人不寫它，只有研究助理手動寫在 `registry.json` 那一筆，build 照抄；機器人更新那一筆時原樣留著（第 6 節）。

審查要用的資料都留著：誰（帳號 id）、什麼時候（issue）、傳了什麼（附件網址、commit 的 diff；repo 放的是解開的原始檔，D106）。

## 11. iPLoT 這邊：「工作坊」

- 每一列：名稱與說明之間多一行「上傳者：@<author>」；索引沒有 `author`（舊的索引）就不顯示。
- 頂層 `notice`：清單最上面、原本那一句提示之後，當文字，不做成表格的一列（`page.html` 用 `list.rows.length` 判斷清單空不空）。介面：新函式讀一次網址、回 `(entries, notice)`；`read_index` 包著它、回傳不變（`test_read_index` 釘著）；`iplot.py` 改用新函式。`page.html` 在 `.hint` 之後、`<table>` 之前加一個 `{notice}` 記號；`render` 多一個參數 `notice=""`，先換 `{notice}`（只換第一個），再用 `rpartition` 換 `{rows}`——順序反過來的話，說明裡剛好寫了「{notice}」這幾個字也會被換掉。
- 每一筆的 `warning`：那一列紅字一行「⚠ <warning>」。
- 三樣都是可選欄位、都當文字（`html.escape`，跟現在的 `description`、`notes` 一樣，D70）；不是字串就當沒有。`read_index` 照舊只要求四項（`NEEDED`）。
- **新的清單放在 `uploads` 這個鍵，`modules` 是空的。** 新的工作坊有 `uploads` 就讀它，沒有才讀 `modules`；所以讀凍結的舊索引照常。舊的工作坊（0.5.1）只讀 `modules`：只改了網址、沒換工作坊的人，看到的是「清單是空的」，不是一份沒有「沒有人審查」、沒有上傳者的開放清單——這份清單以前是研究助理挑過的，看起來會一模一樣。`read_index` 的檢查（`NEEDED`）照舊，套在讀到的那一串上。
- 清單頁開著的時候，那個模組剛好部署了新版，按安裝下載到的 zip 跟清單上的 sha256 對不上。`download` 對不上時丟專用的例外（`ShaMismatch`，繼承 `ValueError`），`Api` 回「無法安裝：下載的檔案跟清單對不上。清單可能剛更新過，關掉工作坊再開一次；再不行就是檔案有問題」。開放上傳之後更新會比以前多，原本那一句看起來像有人竄改。
- 不改：安裝的做法（上面那一句除外）、六種狀態、`.origin`、`.unconfirmed`、`BUNDLED`。核心那一句「是從外面裝進來的」不改（`core/text.py`，D80）。
- 測試（`tests/test_workshop.py`）：上傳者、`notice`、`warning` 都顯示而且跳脫；讀 `uploads`，有 `uploads` 時不讀 `modules`；舊索引（只有 `modules`）照常；不是字串的不顯示。`tests/test_bundled.py::test_shipped_config_points_at_the_workshop_site` 拆成兩個 assert：`UPDATE_URL` 照舊是 `iplot-workshop/update.json`，`WORKSHOP_URL` 是 `iplot-modules/index.json`（名字留著：`docs/02`、`docs/03`、CHANGELOG 都引用它）。`tests/test_version.py` 改成 0.5.2。
- `tests/acceptance_workshop.py`（每一版發佈後對真的網址跑的那支）照兩個網址分開：`--published` 只拿來比 `update.json`；`index.json` 用新的 `workshop.py` 讀得懂、每個 zip 的 sha256 對；核心那一頁從 `UPDATE_URL` 那一層拿；「作業系統是隨附模組」那一項換成檢查 `notice` 那一行與「上傳者」（新清單上不會有隨附模組：保留的名字誰都不能傳）。要等第 9.3 節的種子收完、網站更新之後才跑：它要從清單裝「打開核心原始碼」。不改的話，換網址之後它等 10 分鐘再失敗；`index.html` 那一項與「作業系統」那一列不管怎樣都不會過。

## 12. M7b：工作坊模組「上傳」

R4 只靠 Finder 壓縮也做得到，但 Finder 壓縮會把資料夾裡的東西整個帶上：`.history/`（每一版的 `iplot.py`）、模組自己存的設定與資料。機器人會略過 `.history/`，略不掉模組自己存的東西（例如行事曆的 `設定.json` 裡有自己的路徑）。「上傳」讓人在送出之前看清楚會公開什麼：

- 把模組資料夾拖到「上傳」上（`on_files`），或按下去選一個（`app.choose_folder()`）。
- 檢查：是模組、名稱合規則、不是保留的三個。
- 列出會公開的檔與大小（略過的規則跟機器人同一份；另外預設排除 `.venv/`、`*.app`、`.python`、`.patched` 這類本機狀態，排除了什麼也列出來）；`app.confirm` 問一次。
- 打好 zip，放在 `modules/上傳/待上傳/<名稱>.zip`（打包自己時略過 `待上傳/`），`app.reveal` 在 Finder 指給你看，用標準庫 `webbrowser` 打開上傳表單；剩下的是把 zip 拖進去。
- 不登入、不自己上傳。
- 它自己也從新的工作坊發（名字歸研究助理），以後改它不用換 iPLoT 這邊的東西（D109）。

4. 限制的數字：25 MB（GitHub 附件的上限）、解開 100 MB、2000 個檔、`iplot.py` 1 MB；說明 500 字、notes 1000 字、`ICON` 16 字、`index.json` 2 MB、zip 的原始條目 20000；每個帳號 24 小時收 10 份、每個帳號 20 個名字、`modules/` 超過 800 MB 就不收新名字（這三個是建議）。GitHub Pages 的網站整個不能超過 1 GB，傳的人多了要換地方放 zip。

## 15. 安全（`docs/07` 第 7 節要補的）

**能保證的：**
- 上傳碰不到核心：模組與 `update.json` 在不同的 repo，機器人的 token 只屬於 `iplot-modules`。
- 一個名字只有第一次傳它的帳號能更新；iPLoT 自己要用的三個名字誰都不能傳；隨附模組的名字歸研究助理。看起來一樣的寫法（零寬字元、全形、特別的空白、混用的字母）也一樣。
- 機器人不執行任何上傳的程式碼：只解壓、`ast.parse`、寫檔。zip 一條一條看過：沒有 `..`、絕對路徑、只差大小寫的兩個檔，符號連結略過，大小有上限。
- issue 的字不進 shell；回覆裡的名稱、帳號名、檔名都放在程式碼裡，不會變成連結或 @ 到人。
- repo 放的是解開的原始檔：每一次上傳改了什麼，誰都看得到 diff。

**不能保證的：**
- **任何有 GitHub 帳號的人，都能讓自己的程式出現在每個人的工作坊清單上，這一版沒有人審查。** iPLoT 這邊唯一的關卡跟現在一樣：裝進來的模組第一次執行前問一次（D59），那只是提醒；按了確定，它就用這個使用者的權限做任何事（`docs/07` 第 7 節「不能保證的」第一、二條）。多的只有：清單上看得到上傳者與 `notice`。
- 名字的主人帳號被盜，盜的人就能更新那個名字的模組。
- 下架只擋新的安裝；已經裝了的不會被拿掉。
- 機器人自己的程式在公開 repo 裡：研究助理合併了有問題的 PR，上傳的規矩就可能被改掉。被信任的是研究助理的帳號與 GitHub。
- 被核可的 PR 帶的 workflow 跟機器人共用 concurrency group，可以取消或卡住機器人的那一次跑；研究助理核可之前要看 `.github/`。
- 傳上去的檔進了 git 歷史：下架刪資料夾拿不掉。傳錯、含個資的，要照 GitHub 的〈Removing sensitive data from a repository〉改寫歷史。
- sha256 那一條照舊：不是簽章，`index.json` 與 zip 來自同一個地方。

## 16. 設計決定（寫進 `docs/03`）

- **D100 開放上傳：有 GitHub 帳號的人都能把自己的模組放上工作坊；這一版沒有審查，位置留好（第 8 節）。** 理由：R1、R5；原則 2「所有人都能改原始碼」到現在只做到改自己的那一份，改了要分享出去還得經過研究助理。沒選：研究助理代為發佈（改了的東西只能經過一個人）；誰都能寫同一個 repo（等於誰都能改別人的模組與核心）。代價：第 15 節「不能保證的」第一條。
- **D101 核心與模組分開放：模組在新的公開 repo `iplot-modules`，`WORKSHOP_URL` 指過去；`update.json` 與核心 zip 留在只有研究助理能寫的 `iplot-workshop`。** 理由：R3；開放的那個 repo 裡不能有任何核心通道會讀的東西。沒選：同一個 repo、機器人只准寫 `modules/`（規矩寫錯一次，核心就跟著開放）。代價：兩個網址；`config.py` 要改一行（D108）。怎麼反悔：`WORKSHOP_URL` 指回 `iplot-workshop/index.json`（凍結的那份還在）。
- **D102 上傳口是 issue 表單（`upload` 欄位）＋ Actions 機器人；不用 PR、不用 `pull_request_target`。** 理由：R4（不用 fork、branch）；表單本身就帶上傳者的身分；自動合併別人的 PR 最直接的寫法是 `pull_request_target`，權限太大。沒選：PR＋自動合併；自己架收檔的伺服器（不用 GitHub 帳號，但要自己顧機器、帳號、防灌爆；2026-10-19 比較過，研究助理選 GitHub）。代價：上傳的人要有 GitHub 帳號、要開瀏覽器。怎麼反悔：換入口只動 `receive.py` 讀上傳的那一段，`registry.json`、build、`index.json` 不變。
- **D103 名字歸第一個上傳的帳號（數字 id）；鍵是 NFC＋casefold；寫法要一模一樣；作業系統、更新、工作坊保留；隨附模組與研究助理的名字先登記給研究助理。** 理由：R2；不然誰都能傳一個同名的新版，按「更新」的人拿到的是他的。這不是審查：不判斷內容，只決定名字是誰的。看起來一樣的寫法另外擋（第 5.2 節第 5 步），不然保留與種子擋不住。沒選：名字前面加帳號（`someone/整理桌面`：資料夾名稱就是模組名稱，D02，多一層會變成兩層模組）；先到先得但不記帳號（之後誰都能更新）。代價：名字被搶了只能換名字；帳號被盜，那個名字就被拿走（研究助理手動救）。
- **D104 機器人只做機械檢查、只讀不執行；每次跑都處理所有還沒處理的上傳，每一份各自處理、一份出錯不擋別人；push 成功才回覆、關 issue。** 理由：同事的審查還沒來之前，機器人不判斷內容好不好，只擋放不進工作坊的、會傷到別人電腦上檔案系統的；GitHub 預設只留一個排隊（`queue: max` 補上，每次處理全部是第二道保險）。沒選：只處理觸發的那一份（被取消的就掉了）。
- **D105 版本：有 `CHANGELOG.md` 照 D78，而且要比現在的新；沒有就最後一段自動加一，第一次 `0.0.1`。** 理由：不會寫 CHANGELOG 的人也傳得了；同一個版本傳兩次，裝過的人永遠看不到「可更新」。沒選：一律要 `CHANGELOG.md`（擋掉第一次上傳的人）；用日期當版本（跟 D78 的寫法對不上）。
- **D106 repo 放解開的原始檔；zip 由 build 打，順序與時間固定（每個檔的時間記成 1980-01-01、權限 0644、照路徑排序），內容沒變 sha256 就不變；Pages 由 Actions 部署。** 理由：誰都看得到 diff（審查也要用）；每次上傳都會重打全部的 zip，時間不固定的話每一次 sha256 都變，剛好在部署中途下載的人會對不上。代價：repo 會長大（GitHub 建議 1 GB 以內）。
- **D107 工作坊顯示 `author`、頂層 `notice`、每一筆 `warning`；三個都是可選欄位、都當文字；新的清單放在 `uploads`，`modules` 留空。** 理由：R7、R5；工作坊是隨附模組，換它很貴（D74），這一次一起把審查以後要對用的人說話的位置留好。`uploads`：0.5.1 的工作坊只讀 `modules`，讀不到開放清單，就不會看到一份沒有警語的。代價：`warning` 只有還在清單上的看得到；只改網址、沒換工作坊的人看到空的清單。
- **D108 0.5.2 的包：核心的四樣只動版本號，加上新的 `config.py` 與 `modules/工作坊`；v0.5.1 之後合進來的「行事曆」0.1.1 照進包，「科學計算」不進包（export-ignore，從工作坊發）；核心邏輯不改，不算 D80 的例外；舊的 `index.json` 凍結。** 理由：新下載的人要拿到新的網址與新的工作坊；「更新」不碰 `config.py` 與 `modules/`（D69），已經在用的照 `update.json` 的 notes 手動做兩件事。沒選：重打 0.5.1 的包（同一個版本兩種內容）；不出包（每個新使用者都要手動改）。
- **D109 「上傳」是工作坊模組，不是隨附模組，從新的工作坊發。** 理由：以後改它不用再換 iPLoT 這邊的東西；它只打包、只開網頁，不登入、不上傳。

## 17. 測試

`iplot-modules/tests/`（pytest，用 zip 樣本，不連網；GitHub API 用替身）：

- 收：Finder 壓的（帶 `__MACOSX/`、`._*`、`.DS_Store`、`.history/`、符號連結、設了自訂圖示的資料夾的 `Icon\r`，中文檔名沒標 UTF-8）收得進來，名字是對的中文，略過的列出來。這份樣本要用 `ditto -c -k --sequesterRsrc --keepParent` 對中文名的資料夾真的壓一份，二進位檔放進 `tests/`，註明怎麼產生的：用 `zipfile` 造的會自動標 UTF-8，測試會過、線上會退件。最上層不是一個資料夾、沒有 `iplot.py`、`..`、絕對路徑、反斜線、只差大小寫、Windows 的字元、不是 UTF-8 的檔名（Big5）、宣告大小騙人的 zip——都不收，回對的那一句。
- 名字：第一次歸上傳的人；同一個 id 更新；別的 id 不收；大小寫、相容表意字、NFD 的寫法都算同一個鍵（同一個主人）；相容表意字、NFD 收成 NFC 的那一個寫法；只差大小寫的不收；保留的三個不收；種子登記的不收。保留的排在 `owner_id` 之前（回保留那一句）；下架之後原主人再傳不收；有 `warning` 的被原主人更新之後 `warning` 還在。零寬、方向控制、變體選擇符、韓文填充字、NBSP、全形空白、全形英文、西里爾混拉丁的寫法，撞保留、種子、別人的名字都不收。
- 版本：沒有 CHANGELOG 自動加一；有就照它；沒比較新不收；讀不出的那幾種。種子那一筆沒有 `version` 時照第一次算；全形數字、`1.1` 之後的 `1.01` 不收。CHANGELOG 第一段 60 MB → notes 截到上限，`registry.json`、`index.json` 都在上限以內。
- 一次跑處理好幾份、舊的先；push 失敗不回「收到了」、issue 不關。push 之前研究助理改了 `owner_id` → 這一份照新的 registry 判斷；同一次裡兩個帳號傳同一個新名字 → 舊的拿到，新的回「名字是別人的」；`registry.json` 有重複的鍵 → 讀的時候就停。
- 一份壞的排在最前面（加密、Deflate64、檔名不是合法 UTF-8、deflate 壞掉、巢狀很深的 `iplot.py`），後面那一份照收、照回覆；同一份壞的跑兩次，第二次不再處理。
- push 成功、回覆失敗之後再跑一次：不發第二版、不回「沒收」，只補回覆；公開的檔 2000 個時，回覆在 20,000 字以內。
- build：zip 的形狀跟 `workshop.install` 要的一樣（最上層 `<名稱>/`、有 `iplot.py`）；同樣的內容打兩次 sha256 一樣；`index.json` 的 `modules` 是空清單、`uploads` 用新的 `workshop.py` 讀得懂（拿 `workshop.py` 那一份的副本測，註明來源）；`index.html` 全部跳脫、沒有 script。用種子的 `registry.json` build 一次，`read_index` 讀得懂；一筆壞的（資料夾不在、沒有 `iplot.py`），其他照發；registry 沒登記的資料夾不發。
- 下載：轉址到別的 host 時，替身伺服器收不到 `Authorization`；網址不符合附件前綴的不收。
- 寫進 repo：帶 `.gitignore`、`.gitattributes`（`eol`、`working-tree-encoding`）、子資料夾裡一個 `.git` 檔、`GIT~1/` 的，repo 裡的跟收下的一樣，或整份不收（測試在 `core.ignorecase=false` 下跑，CI 是 Linux）。
- 路徑：`m/a`＋`m/a/b`、`m/a/`＋`m/a`、`m/A/x`＋`m/a/y`、`m//iplot.py` 都不收。
- TITLE：資料夾「隨便取」、`TITLE = "更新"` 的不收；`TITLE` 跟自己的名稱一樣的照收。
- 帳號：`type` 不是 User 的、`ghost` 的，都不收；registry 裡沒有 ghost 的 id。
- 上限：同一個帳號第 11 份（24 小時內）、第 21 個名字不收；`modules/` 超過門檻時新名字不收、更新照收。
- notice、warning：`index.json` 一定有非空的 `notice`；有 `warning` 的那一筆，index 裡有 `warning`；傳一個叫 notice 的模組，`notice` 不變。
- 網址：名稱是 `C#工具`、`a%20b` 的模組，用 `workshop.install` 裝得進去。
- 速率：替身 API 回 429，剩下的不留言、issue 留著，下一次照收；一份上傳只寫兩次。
- iplot.py：一串 10 萬個 `-`、latin-1 加 coding 宣告、含 NUL，各回對的那一句，同一次後面那一份照收。
- NFD：用 ditto 從 NFD 名稱的資料夾（例如「ガイド」）壓的樣本，收下之後 `workshop.install` 裝得進去。
- 回覆：名稱 `@someone`、`#1`、`a`b`，檔名 `` ``` ``，都在程式碼裡、圍欄不會被關掉；回覆裡沒有 `@<owner>`。
- workflow：`run:` 裡沒有 `github.event.issue`；每個 job 都有 `permissions`；action 都釘 sha（讀 yml 檢查）。
