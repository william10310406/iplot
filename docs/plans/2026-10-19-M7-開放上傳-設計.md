# M7 開放上傳：誰都能把自己的模組放上工作坊（設計）

2026-10-19。這份是設計（規格），不是工作單。方向是研究助理在 2026-10-19 的對話裡定的：任何人都能上傳自己的模組；審查不是這一版的事，由另一位同事處理；上傳走 GitHub（上傳的人要有 GitHub 帳號）。細節（D101–D109）是這份提的，研究助理看過再定；定了之後 Claude Code 依這份寫工作單（`docs/plans/2026-10-19-M7-開放上傳.md`）再實作。
前提：核心是 0.5.1。**這個里程碑核心邏輯一行都不改**（D80）。動到的是隨附模組「工作坊」、`config.py`、`tools/publish.py`，另外多一個公開 repo `iplot-modules` 與它的機器人。
參考：`docs/07` 第 6、7、11 節；D54、D69、D70、D71、D73、D74、D77、D78、D79、D80。

## 0. 一句話

有 GitHub 帳號的人，把模組資料夾壓成 zip，在 `iplot-modules` 的「上傳模組」表單拖進去、送出；機器人只做機械檢查——zip 的形狀、名字是誰的——過了就放進 repo、重產清單、更新網站，在 issue 回一句。iPLoT 的工作坊照舊讀一份 `index.json`，每一列多一行「上傳者」。核心的更新（`update.json`）留在只有研究助理能寫的 `iplot-workshop`，上傳碰不到。審查這一版不做，位置留好（第 8 節）。

## 1. 需求

來源：研究助理（2026-10-19）：「我想要的是任何人都能更新工作坊，就是所有人都可以寫自己的模組並且上傳，審查的話目前不是我要解決的事情，會是我的另一個同事去思考解決這類問題的辦法」。比較過自己架收檔的伺服器之後，定「還是以 GitHub」。

- **R1 誰都能上傳**：有 GitHub 帳號就能把自己寫的模組放上工作坊，不用經過研究助理。
- **R2 名字有主人**：上傳的人能更新自己的模組；別人不能用同一個名字蓋掉。
- **R3 碰不到核心**：開放上傳不能讓任何人換掉別人的核心。
- **R4 只用瀏覽器**：上傳不用 git、fork、PR；在 Finder 壓縮、在網頁拖進去。
- **R5 審查留位置**：同事之後接上，不用改上傳方式、不用改清單格式、不用再換一次 iPLoT 這邊的東西。
- **R6 核心不改**（D80）。
- **R7 看得到是誰傳的**：清單上每個模組都標上傳者。

**做好的樣子：**
- 上傳的人：在 Finder 對著模組資料夾按右鍵「壓縮」→ 打開 `iplot-modules` 的「上傳模組」表單 → 把 zip 拖進去、勾「我知道…」、送出 → 一兩分鐘後 issue 裡出現「收到了：「整理桌面」0.0.1，5 個檔…」，issue 關掉 → 再過幾分鐘，任何人在 iPLoT 按「工作坊」，清單上就有「整理桌面」，底下一行「上傳者：@xxx」。
- 傳錯的人：issue 裡一句話說哪裡不對（例如「zip 裡要剛好是一個資料夾…」），issue 關掉；改好再開一個。
- 用 iPLoT 的人：清單最上面多一行「這裡的模組是大家上傳的，沒有人審查…」，每一列多一行上傳者；安裝、更新、覆蓋、第一次執行前問一次，都跟現在一樣。

     build    contents: read

                          ▼
         https://william10310406.github.io/iplot-modules/

iPLoT 的「工作坊」 ───────┘  安裝、更新、覆蓋都跟現在一樣

研究助理 ──git push──▶ iplot-workshop：update.json、核心 zip（不變；上傳碰不到）

| | `iplot-workshop`（已有） | `iplot-modules`（新的） |
|---|---|---|
| 放什麼 | `update.json`、`iPLoT-vX.Y.Z.zip`、核心那一頁；凍結的舊 `index.json` | 模組的原始檔、`registry.json`、機器人；網站是 build 出來的 |

## 4. 上傳表單

`.github/ISSUE_TEMPLATE/上傳模組.yml`（issue form）：

- `name: 上傳模組`，`title: "上傳："`，`labels: [上傳]`。
- `upload`（id `zip`）：標籤「模組的 zip」；說明「在 Finder 對著模組的資料夾按右鍵 →「壓縮」，把壓出來的 .zip 拖進來。一次一個模組。zip 裡的每個檔都會公開。」；`validations: { required: true, accept: ".zip" }`。表單的 `upload` 欄位收 .zip，上限 25 MB。
- `textarea`（id `notes`）：「這一版改了什麼（選填）」；說明「模組裡有 CHANGELOG.md 的話以它為準，這裡不用寫。」
- `checkboxes`（id `agree`，必勾）：「我知道上傳的東西誰都看得到、誰都能下載執行；這個名字之後只有我的帳號能更新。」
- `config.yml`：`blank_issues_enabled: false`。沒有寫入權限的人開 issue，只有表單可以選。

送出之後內文長什麼樣（附件的網址格式、欄位的標題）文件沒寫，Task 0 先看（第 14 節）。

## 5. 機器人

### 5.1 什麼時候跑

- 觸發：`issues: [opened]`、`push`（`main`）、`workflow_dispatch`。
- `concurrency: { group: modules, queue: max }`：一次只跑一個，其他排隊，最多 100 個。不寫 `queue: max` 的話，GitHub 只留一個在排隊，新來的會把排隊中的那一個取消。
- receive 每次都處理**所有**還開著、帶「上傳」標籤的 issue，舊的先。所以某一次被取消、失敗了，下一次（下一份上傳、研究助理 push、手動跑）照樣收；收過的都已經關掉，不會收兩次。標籤沒貼上的情況見第 14 節。
- receive 每次順便確認四個標籤在（「上傳」「已發佈」「沒收」「卡住」），不在就建：表單的 `labels` 只會貼 repo 裡已經有的標籤。所以 repo 建好之後要先跑一次（第一個 commit 的 push 就會跑）。
- `push`（研究助理直接改 repo，例如下架）與 `workflow_dispatch` 一定 build＋deploy；`issues` 只在 receive 收進了東西才 build＋deploy。receive 失敗也一樣：build、deploy 的 `if` 都帶 `!cancelled()`（GitHub 預設前一個 job 失敗或被跳過，後面的全部跳過）。
- receive 用 `GITHUB_TOKEN` push，不會再觸發一次 workflow（GitHub 的規矩），所以 build、deploy 跟在同一次裡面做。
- receive 與 build 的 checkout 都指定 `ref: main`：`issues` 事件預設拿到的 commit 是事件發生那一刻的，看不到前一次 receive 剛推上去的。

### 5.2 一份上傳怎麼收

照順序；哪一步不過就停在那裡、回那一句（第 10 節）。

**每一份各自處理，一份出錯不擋別人。** 從打開 zip（`ZipFile()` 本身就會丟例外）到 `git add`，每一份包在自己的 `try` 裡：
- 已知的例外——`BadZipFile`、`RuntimeError`（加密）、`NotImplementedError`（壓縮法不支援）、`zlib.error`、`EOFError`、`ValueError`、`UnicodeDecodeError`、`OSError`——回第 10 節「zip 打不開或壞了」那一句，貼「沒收」、關掉。
- 其他任何例外（接 `Exception`，含 `MemoryError`、`RecursionError`）——回「機器人處理不了這份上傳，研究助理會看」，貼「卡住」、拿掉「上傳」，issue 留著。它就不會再排進下一次。
- 全部檢查都過了才寫進工作目錄；寫到一半出錯，`git reset --hard` 加 `git clean -ffdx -- modules/<名稱>/` 回到這一份之前，再接著處理下一份。

不這樣做的話：receive 每次都從最舊的收起，一份讓它丟例外的上傳（用任何壓縮軟體加個密碼就做得到）永遠排第一，之後誰的都收不進來，直到研究助理手動關掉它。

1. 上傳的人是一般帳號（`issue.user.type == "User"`）。
2. 內文裡剛好一個 `.zip` 附件，網址在 `https://github.com/` 底下。
3. 下載：逾時 60 秒，超過 25 MB 就停。不帶 token（公開 repo 的附件不用登入）；Task 0 不通才帶。
4. 打開 zip。不用 `extractall`，一條一條看過才讀：
   - **略過**（回覆裡列出來）：`__MACOSX/`、`._` 開頭的檔（Finder 壓縮附帶的）；各台電腦自己的名字 `.history`、`.origin`、`.unconfirmed`、`__pycache__`、`.DS_Store`（不分大小寫，跟 `tools/publish.py`、`workshop.py` 的 `SKIP` 同一組）；`.git/`、`.venv/`；符號連結。
   - 剩下的：剛好一個最上層資料夾 `<名稱>/`，裡面有 `iplot.py`。
   - 每一條路徑（NFC 正規化之後）：不能有 `..`、不能是絕對路徑、不能有反斜線與控制字元、不能有 Windows 不能用的字元（`:*?"<>|`）、不能是保留字（CON、NUL…），每一段結尾不能是 `.` 或空白；同一層不能有只差大小寫的兩個（macOS、Windows 上是同一個檔）；不能有兩條一樣的。
   - 檔名一律照 UTF-8 解：用 `zipfile.ZipFile(f, metadata_encoding="utf-8")` 打開（3.11 起有；只作用在沒標 UTF-8 旗標的條目）。Finder 的「壓縮」寫的檔名是 UTF-8，卻**不標**旗標（2026-10-19 用 `ditto -c -k --sequesterRsrc --keepParent` 驗過：每一條的 `flag_bits` 都沒有 0x800，Python 預設照 cp437 解成亂碼）。解不開（例如舊的 Windows 內建壓縮寫的 Big5）在打開時就丟 `UnicodeDecodeError`：不收，說一句。不要用「解出來的名字有沒有中文」判斷：沒解對的時候名字裡一個中文字都沒有，亂碼的名字照樣過得了名稱規則。
   - 解完每一條路徑做 NFC：ditto 照磁碟上的寫法放，可能是 NFD。
   - 解開合計 ≤ 100 MB、≤ 2000 個檔；用實際讀出來的位元組算，不信 zip 自己寫的大小（擋 zip 炸彈）。
5. 名稱跟核心的 ＋ 同一套規則（`core/create.py` 的 `_bad_name`，D54）。
6. 名字是誰的（第 6 節）。
7. `iplot.py` ≤ 1 MB、`ast.parse` 過得了；說明與圖示照核心的 `meta.read_meta` 讀（docstring 第一段、`ICON`）。有語法錯誤不收：傳上來，別人裝了也跑不起來。說明 ≤ 500 字、`ICON` ≤ 16 字；超過的截短加「…」，回覆裡說一聲。
8. 版本與 notes（第 7 節）。notes ≤ 1000 字，超過的一樣截短；`registry.json` 只存截短之後的。沒有上限的話，一份 60 MB 的 CHANGELOG 第一段壓起來只有一百多 KB：`index.json` 就是 60 MB，每個人按「工作坊」都要下載；兩份讓 `registry.json` 超過 GitHub 的 100 MiB，之後每一次 push 都被拒。build 再擋一次：`index.json` 超過 2 MB 就讓 job 失敗、不部署。
9. `may_publish(upload)`：這一版一律回「可以」（第 8 節）。
10. 寫進去：`modules/<名稱>/` 整個換成這一次的檔；`registry.json` 那一筆更新；commit，訊息「上傳：<名稱> <版本>（@<帳號>，#<issue>）」，加一行 `Co-authored-by` 掛上傳的人。

全部處理完才 push；被拒絕（研究助理剛好也 push 了）就 `pull --rebase` 再 push 一次。**push 成功才回覆、貼標籤、關 issue。** push 不成功，就在每一份 issue 說「這次沒收成，會自動再試」，issue 留著，下一次跑再收。

### 5.3 回覆

- 收到：「收到了：「<名稱>」<版本>，<N> 個檔。網站幾分鐘內更新，之後在 iPLoT 按「工作坊」就看得到。」＋公開的檔、略過的檔（各一個程式碼區塊）。標籤「已發佈」，關掉。
- 沒收：第 10 節那一句。標籤「沒收」，關掉；改好之後開一個新的。
- 檔名一律放在程式碼區塊裡：不會變成連結、不會 @ 到人。

### 5.4 規矩

- **只讀不執行。** 上傳的東西只會被解壓、`ast.parse`、寫進 repo，一行都不會被執行——跟收作業一樣（`docs/07` 第 7 節「科學計算」那一段）。
- **issue 的字不進 shell。** workflow 的 `run:` 裡不寫 `${{ github.event.issue.* }}`；腳本從 API 讀 issue，當資料。
- **最少權限。** workflow 頂層 `permissions: {}`；receive 只有 `contents: write`、`issues: write`；build 只有 `contents: read`；deploy 只有 `pages: write`、`id-token: write`。這個 token 屬於 `iplot-modules`，碰不到 `iplot-workshop`。
- **不用第三方 action**；GitHub 自己的 action 釘 commit sha。
- **不用 `pull_request_target`。** 有人開 PR（例如改機器人），只跑測試（`pull_request`，唯讀），不合併、不部署；合不合併是研究助理的事。
- 機器人只用標準庫（`urllib`、`zipfile`、`ast`、`json`）；呼叫 GitHub API 用 `urllib` 帶 `GH_TOKEN`。

### 5.5 workflow 的樣子（示意）

```yaml
name: 收模組
on:
  issues: { types: [opened] }
  push: { branches: [main] }
  workflow_dispatch:
permissions: {}
concurrency: { group: modules, queue: max }
jobs:
  receive:
    runs-on: ubuntu-latest
    permissions: { contents: write, issues: write }
    outputs: { changed: "${{ steps.receive.outputs.changed }}" }
    steps:
      - uses: actions/checkout@<sha>       # with: { ref: main }
      - uses: actions/setup-python@<sha>   # with: { python-version: "3.12" }
      - id: receive
        run: python -I tools/receive.py
        env: { GH_TOKEN: "${{ github.token }}" }
  build:
    needs: receive
    if: ${{ !cancelled() && (github.event_name != 'issues' || needs.receive.outputs.changed == 'true') }}
    runs-on: ubuntu-latest
    permissions: { contents: read }
    steps:
      - uses: actions/checkout@<sha>       # with: { ref: main }
      - uses: actions/setup-python@<sha>
      - run: python -I tools/build.py site
      - uses: actions/upload-pages-artifact@<sha>   # with: { path: site }
  deploy:
    needs: build
    if: ${{ !cancelled() && needs.build.result == 'success' }}
    runs-on: ubuntu-latest
    permissions: { pages: write, id-token: write }
    environment: { name: github-pages }
    steps:
      - uses: actions/deploy-pages@<sha>
```

## 6. 名字是誰的：`registry.json`

```json
{
  "整理桌面": {"name": "整理桌面", "owner_id": 87654321, "owner": "someone", "version": "0.0.2",
               "notes": "多了一個資料夾", "issue": 12, "updated": "2026-10-21"},
  "作業系統": {"name": "作業系統", "reserved": true}
}
```

- **鍵**是 NFC 正規化再 casefold 的名稱：macOS 的檔名不分大小寫，相容表意字跟本字是同一個（跟 `workshop._bundled` 同一套）。
- 沒有這個鍵 → 第一次上傳，名字歸上傳的人。記**數字 id**（帳號改名也認得）；`owner` 只是顯示用，每次上傳更新。
- 有、`owner_id` 一樣 → 更新。寫法要跟第一次一模一樣（`name` 欄），大小寫或 Unicode 寫法不同就不收：在分大小寫的系統（Linux）上會變成兩個資料夾。
- 有、`owner_id` 不一樣 → 不收。
- `reserved: true` → 誰都不收：作業系統、更新、工作坊（工作坊本來就不覆蓋它們，D74）。
- **種子先登記**給研究助理的帳號：開工、打開核心原始碼、開Terminal、重新啟動、互通、主控面板、行事曆、科學計算。不登記的話，別人可以傳一個「重新啟動」：在用的人那裡它是「版本未知」，按了「覆蓋」，隨附的就換成他的。
- **下架**（研究助理手動）：刪掉 `modules/<名稱>/`，那一筆加 `"removed": true`（名字還是原來的人的，不能馬上被搶），push。只擋新的安裝，已經裝了的不會被拿掉。
- **轉名字、救帳號**（例如原主人的帳號刪了）：研究助理改 `owner_id`，push。

## 7. 版本與「這一版改了什麼」

- **模組裡有 `CHANGELOG.md`**：照 D78（`publish.latest`）讀最上面那一節，版本只認數字與點，而且要比 `registry.json` 裡現在的版本新，不然不收——一樣的版本，裝過的人永遠看不到「可更新」。notes 取那一節第一段；表單那一格不用（回覆裡說一聲）。
- **沒有**：版本自動往上加。第一次 `0.0.1`；之後把現在的版本最後一段加一（`0.1.1` → `0.1.2`）。notes 取表單那一格，沒寫就是空的。
- 兩條都只產生工作坊比得了的版本（`workshop._newer` 只比數字）。

## 15. 安全（`docs/07` 第 7 節要補的）

**能保證的：**
- 上傳碰不到核心：模組與 `update.json` 在不同的 repo，機器人的 token 只屬於 `iplot-modules`。
- 一個名字只有第一次傳它的帳號能更新；iPLoT 自己要用的三個名字誰都不能傳；隨附模組的名字歸研究助理。
- 機器人不執行任何上傳的程式碼：只解壓、`ast.parse`、寫檔。zip 一條一條看過：沒有 `..`、絕對路徑、符號連結、只差大小寫的兩個檔，大小有上限。
- issue 的字不進 shell；回覆裡的檔名不會變成連結或 @ 到人。
- repo 放的是解開的原始檔：每一次上傳改了什麼，誰都看得到 diff。

**不能保證的：**
- **任何有 GitHub 帳號的人，都能讓自己的程式出現在每個人的工作坊清單上，這一版沒有人審查。** iPLoT 這邊唯一的關卡跟現在一樣：裝進來的模組第一次執行前問一次（D59），那只是提醒；按了確定，它就用這個使用者的權限做任何事（這一節「不能保證的」第一、二條）。多的只有：清單上看得到上傳者與 `notice`。
- 名字的主人帳號被盜，盜的人就能更新那個名字的模組。
- 下架只擋新的安裝；已經裝了的不會被拿掉。
- 機器人自己的程式在公開 repo 裡：研究助理合併了有問題的 PR，上傳的規矩就可能被改掉。被信任的是研究助理的帳號與 GitHub。
- sha256 那一條照舊：不是簽章，`index.json` 與 zip 來自同一個地方。

## 16. 設計決定（寫進 `docs/03`）

- **D100 開放上傳：有 GitHub 帳號的人都能把自己的模組放上工作坊；這一版沒有審查，位置留好（第 8 節）。** 理由：R1、R5；原則 2「所有人都能改原始碼」到現在只做到改自己的那一份，改了要分享出去還得經過研究助理。沒選：研究助理代為發佈（改了的東西只能經過一個人）；誰都能寫同一個 repo（等於誰都能改別人的模組與核心）。代價：第 15 節「不能保證的」第一條。
- **D101 核心與模組分開放：模組在新的公開 repo `iplot-modules`，`WORKSHOP_URL` 指過去；`update.json` 與核心 zip 留在只有研究助理能寫的 `iplot-workshop`。** 理由：R3；開放的那個 repo 裡不能有任何核心通道會讀的東西。沒選：同一個 repo、機器人只准寫 `modules/`（規矩寫錯一次，核心就跟著開放）。代價：兩個網址；`config.py` 要改一行（D108）。怎麼反悔：`WORKSHOP_URL` 指回 `iplot-workshop/index.json`（凍結的那份還在）。
- **D102 上傳口是 issue 表單（`upload` 欄位）＋ Actions 機器人；不用 PR、不用 `pull_request_target`。** 理由：R4（不用 fork、branch）；表單本身就帶上傳者的身分；自動合併別人的 PR 最直接的寫法是 `pull_request_target`，GitHub 已經在公開 repo 預設擋這個事件（2026-11-02 起正式執行）。沒選：PR＋自動合併；自己架收檔的伺服器（不用 GitHub 帳號，但要自己顧機器、帳號、防灌爆；2026-10-19 比較過，研究助理選 GitHub）。代價：上傳的人要有 GitHub 帳號、要開瀏覽器。怎麼反悔：換入口只動 `receive.py` 讀上傳的那一段，`registry.json`、build、`index.json` 不變。
- **D103 名字歸第一個上傳的帳號（數字 id）；鍵是 NFC＋casefold；寫法要一模一樣；作業系統、更新、工作坊保留；隨附模組與研究助理的名字先登記給研究助理。** 理由：R2；不然誰都能傳一個同名的新版，按「更新」的人拿到的是他的。這不是審查：不判斷內容，只決定名字是誰的。沒選：名字前面加帳號（`someone/整理桌面`：資料夾名稱就是模組名稱，D02，多一層會變成兩層模組）；先到先得但不記帳號（之後誰都能更新）。代價：名字被搶了只能換名字；帳號被盜，那個名字就被拿走（研究助理手動救）。
- **D104 機器人只做機械檢查、只讀不執行；每次跑都處理所有還沒處理的上傳，每一份各自處理、一份出錯不擋別人；push 成功才回覆、關 issue。** 理由：同事的審查還沒來之前，機器人不判斷內容好不好，只擋放不進工作坊的、會傷到別人電腦上檔案系統的；GitHub 預設只留一個排隊（`queue: max` 補上，每次處理全部是第二道保險）。沒選：只處理觸發的那一份（被取消的就掉了）。
- **D105 版本：有 `CHANGELOG.md` 照 D78，而且要比現在的新；沒有就最後一段自動加一，第一次 `0.0.1`。** 理由：不會寫 CHANGELOG 的人也傳得了；同一個版本傳兩次，裝過的人永遠看不到「可更新」。沒選：一律要 `CHANGELOG.md`（擋掉第一次上傳的人）；用日期當版本（跟 D78 的寫法對不上）。
- **D106 repo 放解開的原始檔；zip 由 build 打，順序與時間固定（每個檔的時間記成 1980-01-01、權限 0644、照路徑排序），內容沒變 sha256 就不變；Pages 由 Actions 部署。** 理由：誰都看得到 diff（審查也要用）；每次上傳都會重打全部的 zip，時間不固定的話每一次 sha256 都變，剛好在部署中途下載的人會對不上。代價：repo 會長大（GitHub 建議 1 GB 以內）。
- **D107 工作坊顯示 `author`、頂層 `notice`、每一筆 `warning`；三個都是可選欄位、都當文字。** 理由：R7、R5；工作坊是隨附模組，換它很貴（D74），這一次一起把審查以後要對用的人說話的位置留好。代價：`warning` 只有還在清單上的看得到。
- **D108 0.5.2 的包：核心的四樣只動版本號，加上新的 `config.py` 與 `modules/工作坊`；v0.5.1 之後合進來的「行事曆」0.1.1 照進包，「科學計算」不進包（export-ignore，從工作坊發）；核心邏輯不改，不算 D80 的例外；舊的 `index.json` 凍結。** 理由：新下載的人要拿到新的網址與新的工作坊；「更新」不碰 `config.py` 與 `modules/`（D69），已經在用的照 `update.json` 的 notes 手動做兩件事。沒選：重打 0.5.1 的包（同一個版本兩種內容）；不出包（每個新使用者都要手動改）。
- **D109 「上傳」是工作坊模組，不是隨附模組，從新的工作坊發。** 理由：以後改它不用再換 iPLoT 這邊的東西；它只打包、只開網頁，不登入、不上傳。

## 17. 測試

`iplot-modules/tests/`（pytest，用 zip 樣本，不連網；GitHub API 用替身）：

- 收：Finder 壓的（帶 `__MACOSX/`、`._*`、`.DS_Store`、`.history/`，中文檔名沒標 UTF-8）收得進來，名字是對的中文，略過的列出來。這份樣本要用 `ditto -c -k --sequesterRsrc --keepParent` 對中文名的資料夾真的壓一份，二進位檔放進 `tests/`，註明怎麼產生的：用 `zipfile` 造的會自動標 UTF-8，測試會過、線上會退件。最上層不是一個資料夾、沒有 `iplot.py`、`..`、絕對路徑、反斜線、符號連結、只差大小寫、Windows 的字元、不是 UTF-8 的檔名（Big5）、宣告大小騙人的 zip——都不收，回對的那一句。
- 名字：第一次歸上傳的人；同一個 id 更新；別的 id 不收；大小寫、相容表意字、NFD 的寫法都算同一個名字；寫法不同不收；保留的三個不收；種子登記的不收。
- 版本：沒有 CHANGELOG 自動加一；有就照它；沒比較新不收；讀不出的那幾種。CHANGELOG 第一段 60 MB → notes 截到上限，`registry.json`、`index.json` 都在上限以內。
- 一次跑處理好幾份、舊的先；push 失敗不回「收到了」、issue 不關。
- 一份壞的排在最前面（加密、Deflate64、檔名不是合法 UTF-8、deflate 壞掉、巢狀很深的 `iplot.py`），後面那一份照收、照回覆；同一份壞的跑兩次，第二次不再處理。
- build：zip 的形狀跟 `workshop.install` 要的一樣（最上層 `<名稱>/`、有 `iplot.py`）；同樣的內容打兩次 sha256 一樣；`index.json` 用 `workshop.read_index` 讀得懂（拿 `workshop.py` 那一份的副本測，註明來源）；`index.html` 全部跳脫、沒有 script。
- workflow：`run:` 裡沒有 `github.event.issue`；每個 job 都有 `permissions`；action 都釘 sha（讀 yml 檢查）。
