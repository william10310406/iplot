# M8：「回報與討論」的名字怎麼保留（評估）

2026-10-24。研究助理問：「回報與討論」會經手錯誤報告，不想靠 M8 工作單 Task 13 搶先上傳來佔名字；評估在上傳機器人加一份保留名單（所有隨附模組的名字），只有 repo 擁有者能用這些名字上傳；也說明現在隨附模組和工作坊上同名的模組誰優先。**這份只是評估，M7（iplot-modules）一行都沒改**；兩個 repo 都只讀，原型做在暫存的複本裡。行號是 iplot-modules 37481e1、iPLoT m8-report dc6f9a6 的。

## 一、結論

- **現在就有一個機制能做到「只有研究助理能傳這個名字」**：`registry.json` 裡登記一筆、`owner_id` 是研究助理（D103 的「隨附模組的名字先登記給研究助理」）。其他十一個隨附模組的名字都已經這樣登記或保留了，**只差「回報與討論」**。這個機制在真的網站上用過：#15（第二個帳號傳「行事曆」）被擋，回的是「這個名字已經是 @william10310406 的」。
- 建議 **A：現在就在 `registry.json` 登記「回報與討論」給研究助理**（只改資料、不改機器人），再加一個只在測試裡的核對，讓下一個新的隨附模組沒登記時有測試會紅。
- 研究助理提的 **B（機器人裡一份隨附模組名單，只有 repo 擁有者能第一次登記）做得到**，原型 24 個新測試全綠、其他沒有退步；它比 A 多的是「以後新的隨附模組忘了登記也擋得住」與「綁的是 repo 擁有者、不是寫死的帳號 id」。代價是改動正在上線的機器人；而它的 PR 現在一定是紅的（兩個早就存在的問題，見第六節）。
- **不建議 C（在 iPLoT 的工作坊那一頭擋）**：最需要保護的 0.5.x 使用者永遠拿不到新的工作坊；把「回報與討論」放進工作坊的 `BUNDLED` 又會讓它的遮蔽修正永遠無法從工作坊發（D74）。
- **在名字保留好之前，不要 push m8-report**：iPLoT 是公開的 repo，M8 的工作單與設計直接寫著「這個名字現在誰都能先傳」。

## 二、機器人現在怎麼判斷一個名字

- 鍵是 NFC＋casefold（`tools/registry.py:72-73`）。`check_name`（`:107-115`）依序擋：不合規則的名字、看不見的字、跟 registry 裡別人的名字太像（`similar_to`，`:97-104`，**只比 registry 裡有的**）。
- `owner_refusal`（`:118-129`）：registry 裡**沒有這個名字就回 None**（`:118-121`）——任何帳號都能第一次傳；有的話依序看 `reserved`（誰都不能傳）、`removed`、名字是別人的（比 `owner_id` 與上傳者的數字 id）、大小寫要跟第一次一樣。
- 上傳者是 issue 的 `user.id`（`tools/receive.py:229`），不看 `author_association`；`who_refusal`（`:201-208`）只擋不是 User 的帳號與 ghost。機器人不讀 repo 擁有者的 id。
- `TITLE` 也一樣：registry 有的名字、或跟別人的名字太像，才擋（`tools/source.py:80-85`）。
- 每個帳號最多 20 個名字（`registry.py:23`、`:147-159`，種子也算）；研究助理現在 9 個，加「回報與討論」是 10 個。

**現在登記了什麼**（`registry.json:1-98`）：作業系統、更新、工作坊是 `reserved: true`（誰都不能傳，研究助理也不行）；開工、打開核心原始碼、互通、主控面板、行事曆（已經上傳過，有版本）與 開Terminal、重新啟動、科學計算（只有種子、沒有版本）的 `owner_id` 是研究助理（71483597）；另外「上傳」也是研究助理的種子（M7b 的工作坊模組，不是隨附模組）。m8-report 追蹤的 11 個隨附模組全都涵蓋了；**「回報與討論」沒有**（它在 M8 Task 3 才進 iPLoT）。網站上現在的 `index.json` 沒有它、沒有開著的 issue；公開的 iPLoT main（7f26d30）沒有提過這個名字。

## 三、隨附模組與工作坊上同名的模組，誰優先

**沒有「優先」這個規則：`modules/<名字>` 就是唯一的一份，面板一個資料夾一格**（`core/scan.py:28-39`、`:79-90`）。決定電腦上跑的是誰的程式碼，是使用者在工作坊按了什麼：

| 這台電腦上的狀態 | 工作坊顯示 | 按下去 |
|---|---|---|
| 包裡帶的（沒有 `.origin`） | 「版本未知」、按鈕「覆蓋」（`workshop.py:157-159`） | 同一列先問一次（`:390`、`:416-426`）；舊資料夾整個存進 `.history/`、放 `.unconfirmed`、把包蓋上去（包裡沒有的檔留著）、寫 `.origin`（`:308-369`）。之後這個資料夾跟著**清單上那個名字的主人**的版本走 |
| 沒有這個資料夾 | 「未安裝」、按鈕「安裝」 | 不先問就裝；第一次執行時問一次「是從外面裝進來的」（D59） |
| 從工作坊裝的、清單上有新版 | 「可更新」、按鈕「更新」 | 同上 |
| 作業系統、更新、工作坊（`BUNDLED`，`:32`） | 「隨附模組」、沒有按鈕 | 工作坊永遠不覆蓋 |

「更新」（核心的更新）一律不碰 `modules/`（`modules/更新/update.py:4`、`:19`）。所以：包裡的隨附模組在使用者自己按「覆蓋」之前一直是那一份；工作坊不會悄悄換掉它。但只要按了，名字的主人是誰，使用者拿到的就是誰的程式碼。

## 四、如果「回報與討論」這個名字被別人拿走

M8 的面板照路徑找 `modules/回報與討論`，那是個模組就畫出「回報這個問題」，按下去把**還沒遮過的** `ErrorInfo` 整個交給它的 `on_error`：出錯檔案的絕對路徑（家目錄、帳號名）、整段 traceback、`error.module`（可能就是學生資料夾的名字與學號）。遮蔽是模組自己做的。

- **會中的人**：(1) 每個照 0.6.0 notes 做的 0.5.x 使用者——notes 叫他們「①「回報與討論」按「安裝」」，資料夾本來不在，一按就裝，接著那一次「從外面裝進來的」他們本來就被告知會出現；(2) 新下載 0.6.0、把「版本未知」的隨附那一份按了「覆蓋」的人（文件同時叫他們覆蓋互通，很容易一起按）。
- **之後每一次回報**都跑那個人的程式、拿到原本要遮的資料；使用者本來就預期會開一個 GitHub 登入頁，要釣魚也很容易。核心的更新不碰 `modules/`，這個狀態會一直留著。研究助理也沒辦法從工作坊發遮蔽的修正（機器人會回「名字是別人的」）；救回來要手動改 `owner_id`，還要發一個比對方高的版本（機器人不收不比較新的版本，裝過的人看不到比較低的版本是「可更新」）——M7 設計第 6 節為「重新啟動」寫過同樣的情形。就算對方沒有惡意，他的模組沒有 `on_error`，那顆鈕也就壞了。
- 機率現在不高（名字還沒公開），影響很大而且會留很久。新的不是「能跑程式」（任何確認過的工作坊模組本來就能），而是**面板會把錯誤報告送到這個名字**。

## 五、三個做法

### A：只改資料——在 `registry.json` 登記給研究助理（建議）

- **改什麼**：iplot-modules 的 `registry.json` 在「車車」之後加一筆 `"回報與討論": {"name": "回報與討論", "owner_id": 71483597, "owner": "william10310406"}`。跟種子當初（39ab605）與下架同事測試（37481e1）一樣，直接 commit 到 main。
- **擋得住什麼**（原型對真的 `registry.py` 函式核過）：別的帳號傳「回報與討論」→「名字是別人的」；`回報 與討論` →「太像」；名字後面藏一個零寬字元 →「看不見的字」；別的模組 `TITLE = "回報與討論"` →「TITLE 已經被用了」；研究助理自己傳 → 照常收。
- **push 之後**：觸發「收模組」（receive → build → deploy）。種子沒有版本，build 不發佈任何新東西（`tools/build.py:108-113`）。之後 Task 13 Step 1 就只是一個種子的第一次上傳，不是搶。
- **push 之前**：`gh issue list -R william10310406/iplot-modules --state open` 是空的（現在是）；用 `python -I` 的 `read_json_strict` 讀一次確認 JSON 沒壞——壞掉的話 receive 與 build 會停到修好為止。
- **建議一起做（只有測試）**：修掉 `tests/test_seed.py` 兩個寫死上線前資料的測試，並加一個核對：隔壁 iPLoT 追蹤的每一個最上層模組，在 registry 裡都要是 `reserved` 或 `owner_id` 是研究助理。原型：A 做了、iPLoT 有「回報與討論」→ 綠；registry 還沒登記、iPLoT 有它 → `AssertionError: ['回報與討論']`。限制：只在兩個 clone 都在的機器上跑；而且「回報與討論」要等 M8 Task 3 commit 之後才會觸發——現在這個空檔它抓不到，所以 A 本身還是要先做。

### B：機器人加一份隨附模組名單，只有 repo 擁有者能第一次登記（研究助理提的）

原型（暫存的 iplot-modules 複本）：

- `tools/registry.py` 加 `BUNDLED`（十二個名字：現在的十一個隨附模組＋「回報與討論」）與 `BUNDLED_BY_KEY`；`owner_refusal`：registry 裡**還沒有**這個名字、它在 `BUNDLED` 裡、上傳者不是 repo 擁有者 → 回現有的 `reserved` 那一句（不加新的句子，README 的拒收表不用改）；擁有者自己要用 `BUNDLED` 裡的大小寫。`similar_to` 與 `TITLE` 也擋「跟還沒登記的隨附名字太像」。
- **registry 已經有的名字照 registry**，訊息一字不變（包括「名字是別人的」）。這樣環境變數拿不到的時候，也擋不住研究助理傳已經登記的互通 0.2.0。
- repo 擁有者的 id 從 Actions 每個 job 都有的 `GITHUB_REPOSITORY_OWNER_ID` 讀（`receive.owner_from_env`；不是 ASCII 數字就當沒有）；拿不到就**對還沒登記的隨附名字一律擋**，stderr 說一句。
- 新測試 `tests/test_bundled_names.py` 24 個（別的帳號拿不到、擁有者可以、不知道擁有者就誰都不行、已登記的照 registry、大小寫、太像、TITLE、環境變數的各種壞值、從 `receive.main` 跑到底兩個、名單本身是 NFC 而且合規則、隔壁 iPLoT 追蹤的每個模組都在名單裡）。結果：新檔 `24 passed`；全套 `2 failed, 579 passed`（2 個是早就紅的 `test_seed`，第六節）；沒有隔壁 iPLoT 時 `4 skipped`；`ruff check tools tests` 乾淨。在 iPLoT 的複本多加一個追蹤的模組，隔壁那個測試就紅：`AssertionError: ['新隨附']`。
- **比 A 多的**：以後新的隨附模組忘了登記也擋得住；綁的是「這個 repo 的擁有者」而不是寫死的 id。
- **代價與風險**：改正在上線的機器人（push 到 main 就部署）；名單要跟 iPLoT 的隨附模組同步（兩份），所以要再加一張兩邊共用的表，讓 iPLoT 自己的 CI 在多了隨附模組時紅（像 M7 的 `tests/test_rules_table.py`）；`GITHUB_REPOSITORY_OWNER_ID` 是 GitHub 文件寫的預設變數，這個 repo 的 runner 上有沒有**還沒實際驗過**；repo 轉到組織名下時擁有者 id 會變，還沒登記的隨附名字就誰都傳不了（fail closed）；B 的 TITLE 規則也擋研究助理把隨附的名字當別的模組的 TITLE（現在沒有模組設 TITLE）。
- **它的 PR 現在一定是紅的**：見第六節，那兩件要先修。

### C：在 iPLoT 那一頭擋（不建議）

- 工作坊本身在 `BUNDLED`、「更新」不碰 `modules/`：0.5.x 的使用者（最需要保護的那一群）手上的 `workshop.py` 永遠是舊的，iPLoT 這邊加什麼檢查都到不了他們。
- 把「回報與討論」加進 `workshop.BUNDLED`：依 D74 它就永遠不能從工作坊更新，遮蔽的修正只能叫大家手動複製；0.6.0 notes 的第①件也做不成。
- 「清單上的作者是研究助理才准覆蓋」：`index.json` 只有 build 當下解出來的顯示用帳號名 `author`，沒有 `owner_id`，`.origin` 也不記；靠它不牢。

## 六、順便查到、跟這件事有關的既有問題（都沒有改）
