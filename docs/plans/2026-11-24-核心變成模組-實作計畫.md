## 1. 卡住的根因（要根治的東西）

- `core/runner.py` 跑模組時改整個程序共用的狀態：工作目錄、`sys.argv`、stdout／stderr、`builtins.input`、`sys.modules`、`sys.path`。**所以同一個程序裡一次只能跑一個模組**，網頁面板只好用一條工作執行緒排隊。
- `app.page` 的規格是「視窗關掉才回來」，頁面開著就一直佔著那條執行緒，後面按的都在排隊。
- 歷來只在個別模組補「另開程序」（行事曆 D89、0.7.3 `separate.py`、0.8 三份 `_spawn` 抄本），沒補的模組（車車、自己寫的、工作坊裝的）照樣卡；補了的另開失敗時也退回面板程序裡開，還是卡。

**根治：模組的程式碼永遠不在面板的程序裡跑。** 每按一次，核心開一個新程序跑那個模組；那個程序愛改什麼全域狀態都只影響它自己。這樣核心就是作業系統的角色：開程序、轉接、收結果。

## 2. 程序模型（Q1 推薦的做法）

```
主程序：開機程式 → 核心 → 面板（main 的提供者，佔主執行緒）
   │  每按一次
   ├─ 工作程序 A：核心的 worker → runner 跑模組 A（在它自己的主執行緒）
   │     app.log / app.ask / app.confirm / app.rescan … → 管道 → 主程序的面板
   │     app.page → 在 A 自己的程序開視窗（主執行緒是它自己的）
   └─ 工作程序 B：同上，跟 A 同時跑，互不排隊
```

規則（全部寫進核心，總共一條判斷，核心仍不認任何角色名字）：

1. **模組程式碼只在工作程序裡跑。** 主程序裡只有核心和面板（`main` 的提供者）。
2. **`app.<名字>` 與 `app.call(角色)`：提供者是面板（`main` 的那個模組）→ 經管道到主程序執行；其他提供者 → 在呼叫者自己的工作程序裡直接執行**（跟現在的 `app.run` 一樣是同步的）。所以要開視窗的「頁面」要做成一個獨立的小模組「頁面」（提供 `app.page`），不是面板，這樣它就在工作程序裡開視窗。
3. **管道協定**：JSON 一行一則（`{"id", "op", "args"}`／`{"id", "value"|"error"}`），只用標準庫（`subprocess` 的 stdin/stdout）。路徑、`ModuleInfo`、`Result`、`ErrorInfo` 有固定的編碼；別的型別過不了管道就回一個清楚的錯誤，不默默變字串。
4. **`app.memory`**：主程序替每個模組留一份；工作程序開始時拿到一份，結束時交回。兩個同時跑的同一個模組，後結束的那份留下（寫進 docs/api.md）。
5. **輸出**：`print` 一行一行即時送回訊息區（現在是跑完才一起出現）。
6. **結束與當掉**：面板可以列出正在跑的模組並停掉它（送 terminate）；工作程序意外死掉，核心把它變成一個 ErrorInfo（「X 意外結束（代碼 n）」），面板照常。
7. **好處順帶拿到**：tkinter／turtle 的模組又能用了（工作程序的主執行緒是它自己的；`NoTk` 可以拿掉）；一個模組當掉拖不垮面板；`separate.py`、三份 `_spawn` 抄本、行事曆的另開全部收掉。
8. **代價**：每按一次多一次 Python 啟動（約 0.1–0.3 秒，外接碟第一次較慢）；按下的順序不再保證是執行完成的順序（兩次按同一個寫同一個檔的模組，自己要處理）。

保留的承諾：工作程序裡 `"core.runner"` 照樣在 `sys.modules`（設計稿第 9 節永久保留的那一小段）。

## 3. API 版本（Q2 推薦）

- `app.api_version` = 6，意思是「核心指令集第 6 版」。`docs/api.md` 開頭放一張表：每一版加了什麼。**只加不減**：要拿掉東西就是 7，而且舊的那一版還要能跑一個大版本。
- 模組頂層可以寫 `MIN_API = 6`（ast 讀，不執行）。核心按下前比對：不夠就不開程序，訊息說「這個模組要 iPLoT 的指令集第 6 版，你的是第 5 版，請按『更新』」。
- 6 相對 5：`app` 的成員全部保留（改成經管道），新增 `app.running()`（正在跑的模組）與 `app.stop(info)`；`app.page` 的規格從「關掉才回來」不變，但只卡住自己那個程序。
- CI：`tests/test_interfaces.py` 釘住每一版的成員清單；第 6 版的清單少了第 5 版的任何一個就紅。

## 4. 分步（每一步一個 PR，草稿；都能從零啟動、舊模組照跑）

### 第 1 步：模組先斷掉對核心內部的依賴（只改模組，核心不動）
- `deps_allow.json` 標 0.9 的全部清掉：互通 import `core.*`（R2）、`sys.modules` 看 `ui.web`／`ui.tk`（R3，改問面板提供的 `panel.kind`）、行事曆與 linebot行事曆 import `core.scan`（`MARKER` 抄一份並登記抄本）、回報與討論的 `report.py`。
- 驗收：`python3 tools/check_deps.py` 列出的 0.9 項目為 0；所有測試綠。

### 第 2 步：程序模型（核心）＋ API 6 —— **卡住在這一步修好**
- 先寫測試（會紅）：`tests/test_concurrency.py`
  - 真的開工作程序；模組 A 呼叫 `app.page`（用不開視窗的假頁面提供者，等一個事件才回來）；A 開著時按模組 B（沒寫任何另開的程式，代表車車那一類）；**B 要在 1 秒內開始跑、跑完**，A 仍開著。
  - A 的程序被殺掉：面板收到一個錯誤，B 照常。
  - B 改工作目錄、`sys.argv`、`input`：A 看不到。
- 核心新增 `core/worker.py`（工作程序的入口）、`core/pipe.py`（協定）；`Core.press` 改成開程序；`App` 在工作程序裡是代理。
- 新的隨附模組「頁面」：`PROVIDES = {"app.page": "page"}`，用 pywebview 在自己的程序開視窗（從 `ui/web.py` 的 `page` 搬出來）。
- 面板（還在 `ui/`）的工作執行緒拿掉排隊：按下只是「開程序」，立刻回來。
- 收掉：互通 `separate.py`、工作坊／回報與討論／行事曆／主控面板的 `_spawn` 抄本、`NoTk`。各模組升版、寫 CHANGELOG。
- 驗收（在 William 的 Mac、全新資料夾，交給查卡住的那個 thread 用它的探針做）：頁面開著時按車車、打招呼、行事曆，各自 1 秒內開始跑；連開三個頁面；關掉其中一個不影響其他。

→ **發 0.9.0**（William 同意後）。

### 第 3 步：面板搬進 `modules/面板/`
- `ui/web.py`、前端、`ui/install.py`（pywebview 安裝）、`ui/tk.py`（備用面板）搬進 `modules/面板/`，`PROVIDES = {"main": "start", "app.ask": …, "app.confirm": …, "app.log": …, "app.choose_files": …, "app.choose_folder": …, "panel.kind": …}`。
- 錯誤鈕、學生作業判斷搬到「回報與討論」「科學計算」（角色 `error`、`error.button`）。`ui/errlog.py` 的「沒接住的例外寫記錄」留在核心（那是執行的一部分）。
- 麵包屑、群組、上一層、新增模組都是面板的事；核心只給 `find()`。
- 核心沒有 `main` 提供者時：開約 40 行的 tkinter 清單（列模組、按一下就跑），一定開得到工作坊。

### 第 4 步：核心搬進 `modules/核心/`，開機程式凍結
- `main.py` 換成開機程式（約 50 行，只用標準庫）：檢查 Python 版本 → 載入 `modules/核心/` → 失敗（例外、語法錯、5 秒內沒回報「`main` 開起來了」）就載入「上次成功開機」的那份（`.local/核心.good/`）→ 再失敗就用隨附的那份 → 都壞了用 `print` 說一句。成功開機的那一份由開機程式自己複製到 `.local/核心.good/`。
- 隨附的唯讀種子放在包裡的 `core/`（見第 5 節為什麼叫這個名字）：`core/__init__.py` 只有版本號，`core/seed/` 放核心、面板、頁面、更新等隨附模組的原始版本。
- 隨附同步（現在的 `core/bundled.py`）：放在核心模組裡（`modules/核心/seed.py`）。它的工作是「讓系統起得來」：新加的隨附模組裝上、使用者沒改過的換新、改過的不碰（D156 的規則照舊）。這是核心裡唯一跟「更新」沾邊的東西，理由：更新模組自己可能是舊的，不能靠它把新的面板放進來。
- CI：`tools/boot.sha256` 鎖開機程式，改了就紅；`modules/核心/` 裡不准出現角色字串（`"main"` 除外）；核心模組、面板模組各有行數上限，只降不升；模組不准 import 核心模組的內部（R2 從 `core` 換成核心模組）。

### 第 5 步：從 0.8 更新上來的路
- 0.8 的「更新」模組只認 `core/`、`ui/`、`main.py`、`requirements/` 四樣，版本號讀 `core/__init__.py`。所以 1.0 的包**照樣有這四樣**：`core/` 變成唯讀種子（第 4 步）、`ui/` 只剩一個說明檔、`main.py` 是開機程式。舊的「更新」換完四樣、重新啟動，新開機程式從 `core/seed/` 把核心與面板放進 `modules/`，就起來了。
- 驗收：真的拿線上的 0.8.0 包當舊安裝，用它的「更新」換成 1.0 的包，重新啟動，面板開得起來、舊模組照跑；刪掉 `modules/` 從零啟動也起得來；把 `modules/核心/iplot.py` 故意弄壞，開機程式退回上一份並說一句。

→ **發 1.0.0**（William 同意後）。

## 5. 防屎山（每一步都上 CI，不靠人記）

1. 開機程式雜湊鎖死。
2. 核心模組裡沒有角色字串（`main` 除外）、沒有任何其他模組的名字。
3. 核心模組、面板模組、開機程式各有行數上限，只降不升（沿用 `tools/limits.json`、`exceptions.json`）。
4. 管道協定只有一份（`core/pipe.py` → 第 4 步搬進核心模組），面板與工作程序都 import 它，不准各寫一份。
5. 模組裡不准再出現「另開程序」的寫法（R11 擴大：`subprocess.Popen(sys.executable, …iplot.py)` 一律紅），要另開就交給核心。
6. 第 2 步的「頁面開著時按別的模組 1 秒內開始跑」是常駐測試，不是一次性驗收。

## 6. 規模與風險（說清楚）

- 2700 多個測試裡，綁著 `Core`、`ui/` 內部的估一半要改寫或搬進模組；第 2 步最大。
- 第 2 步之後，模組裡任何「只在同一個程序才成立」的寫法會壞：例如把東西存在模組層級的全域變數、期待下次按還在（現在每次都重新執行 iplot.py，所以本來就不成立，風險小）；或兩個模組靠同一個 Python 物件溝通（目前隨附的沒有，工作坊裝的要掃一遍）。
- Windows：開程序與管道用標準庫，但未經實機驗證；CI 有 Windows，至少測試會跑。
