# 核心只負責執行：重新設計（設計稿，未改程式）

寫於 2026-11-23。對照的程式：`origin/main` 的 `6875078`（核心 0.7.4）。取代 11-18 的〈核心回收：六個擴充點〉草稿的方向；那份的實作細節（行數清點、各模組會斷的地方）仍可參考。

William 的目標（原話整理）：
- 核心什麼都不知道，只負責執行。
- 像 CPU／GPU：除了溢位（資源或格式錯誤）以外什麼都能執行。
- 主控面板、任何功能，**甚至核心本身**，都是模組。

---

## 1. 結論先講

1. **11-18 草稿做完，核心還是會繼續長。** 它把寫死的模組名換成了寫死的「掛勾名」（`MENU`、`ERROR_BUTTON`、`ON_START`、`PANEL`、`NAV`、`PROCESS`）。每多一種「模組想伸進去的地方」，核心就要多認一個名字、多一段分派。膨脹的速度從「每個功能」變成「每種擴充點」，慢一點，但不會停。
2. **真正會停的做法：核心只提供一套固定的「指令集」，不解讀任何名字的意思。** 模組之間用字串互相找（「誰提供 `menu`？」），字串的意思由模組之間約定，核心只負責找到並執行。新功能需要新的擴充點時，改的是兩個模組，核心一行不動。
3. **「核心本身也是模組」做得到，但一定要留一小段永遠不改的開機程式**（CPU 的重置向量／BIOS 那一層）。這一段沒辦法是模組，因為要有人去載入第一個模組。做法是把它壓到約 50 行、凍結、用 CI 鎖住雜湊；核心（執行器）本身放進 `modules/`，可以更新、可以壞了退回上一版。
4. **估計：** 永不改的開機程式約 50 行＋核心模組約 250 行，取代現在的 core 695＋ui 約 1050＋main.py 195（共約 1940 行，全部隨核心發佈）。

## 3. 新架構：三層

```
開機程式（凍結，約 50 行）   ← 唯一不是模組的東西；CPU 的重置向量
   └─ 核心模組 modules/核心/   ← 執行器：找模組、執行、轉接；約 250 行，可更新、可退回
        └─ 其他一切都是模組：面板、作業系統、工作坊、更新、回報、導覽列、整理、版本紀錄……
```

### 3.1 指令集：核心模組只做這幾件事

把它想成 CPU 的指令集。指令的格式固定，指令的「用途」核心不管。

| 指令 | 意思 |
|---|---|
| `find()` | 照 `ROOTS` 找所有模組（有 `iplot.py` 的資料夾），用 ast 讀頂層常數，**不解讀內容** |
| `run(模組, 函式名, *參數)` | 執行；工作目錄、輸出收集、例外變成資料（ErrorInfo）。這就是唯一的「執行」 |
| `providers(角色)` | 頂層宣告 `PROVIDES = {"角色": "函式名", ...}` 的模組，依固定順序 |
| `call(角色, *參數)` | 交給第一個提供者執行，回傳結果；沒有提供者回 `None` 並記一行 |
| `each(角色, *參數)` | 交給所有提供者，依序執行，收集結果；某一個壞了不影響其他 |
| `memory`、`home`、`config`（原樣的 dict） | 模組拿得到的基本狀態；`config` 核心只讀 `ROOTS`，其他鍵原樣交給模組自己讀 |

「溢位」對應的是：檔案讀不到、語法錯、例外、逾時。這些核心接住、變成資料交給 `each("error")`，核心自己不倒。除此之外，模組要做什麼核心都不審、不擋。

核心模組裡**不准出現任何角色字串**，只有一個例外：`"main"`（開機後把主執行緒交給誰）。CI 掃字串擋。

### 3.2 `app` 改成開放的

現在 `app.open(path)` 是核心寫死的方法，內部再去找「作業系統」。改成：`app` 上找不到的屬性，一律轉成 `call("app.<名字>", ...)`（Smalltalk 的 `doesNotUnderstand:` 就是這樣：物件不懂的訊息交給別人處理）。

- `app.open(p)` → `call("app.open", p)` → 作業系統模組宣告 `PROVIDES = {"app.open": "open", ...}` 接住。
- `app.page(...)` → 面板模組提供。tkinter 面板不提供，就自然沒有。
- 將來 `app.notify(...)`、`app.clipboard(...)`：寫一個提供它的模組就有了，核心不動、`api_version` 不升。

舊模組照用 `app.open`、`app.page`，不用改，這就是過渡的相容層。

### 3.3 面板只是 `main` 的提供者

開機後核心呼叫 `call("main")`，把主執行緒交出去。現在的網頁面板（`ui/web.py`＋前端＋pywebview 安裝）整包搬進 `modules/面板/`，宣告：

```python
PROVIDES = {"main": "start", "app.page": "page", "app.ask": "ask", "app.confirm": "confirm", "app.log": "log"}
```

面板自己問 `providers("menu")` 長出右鍵選單、問 `providers("page.top")` 讓導覽列注入頁面、問 `providers("error.button")` 長出「回報這個問題」。這些字串只有面板和那幾個模組知道。要再多一種擴充點：改面板和新模組，核心不動。

麵包屑、群組、「上一層」、快照、改名、刪除，全部是面板或面板呼叫的模組的事。

### 3.4 核心本身是模組：誰來載入第一個？

這是 William 這個要求的關鍵，直接講會碰到的問題。

**問題 1：雞生蛋。** 「找模組並執行」本身就是核心。如果核心是模組，就要先有東西去找它、執行它。這個東西不能是模組。CPU 也一樣：通電後跳到一個寫死的位址（重置向量），那裡的 ROM 程式不是作業系統的一部分，也不能被作業系統替換掉。

**做法：凍結的開機程式（`main.py` 改寫，約 50 行），只做四件事：**
1. 檢查 Python 版本（現在 `main.py` 已有）。
2. 讀 `modules/核心/` 的版本指標，用檔案路徑載入那個核心模組。
3. 載入失敗（語法錯、例外、5 秒內沒回應）就載入上一個能開的版本（`.history` 裡記成「上次成功開機」的那份）。
4. 兩個都壞了：只用 `print`／內建的 tkinter 說一句哪裡壞了，給「換回隨附的核心」一個鈕。

這段程式的規則：**永遠不改**。CI 存它的雜湊，改了就紅；真的要改（例如 Python 4），當成換硬體，另開一個大版本。

**問題 2：核心模組壞了，修它的工具也壞了。** 工作坊、更新都跑在核心上。所以「上一個能開的版本」必須由開機程式自己判斷，不能交給任何模組。判斷規則只有一條：核心模組回報「`main` 已經開起來」，開機程式就把這一份記成成功；沒回報就是失敗。手機系統的 A/B 分區（一份在用、一份備著，開不了就切回）是同一個想法。

**問題 3：一般模組也能宣稱自己是核心嗎？** 不行。開機程式只看 `modules/核心/` 這一個資料夾，不掃、不看宣告。換核心只有兩條路：「更新」寫進那個資料夾，或使用者自己改。這是整個系統唯一寫死的路徑，也是安全上的底線：工作坊裝的模組碰不到開機的路徑。

**問題 4：工作坊「在任何核心版本都要能開」。** 新設計反而更容易保證：核心模組對外的指令集（3.1 的六樣）凍結成「指令集 1」，之後只加不減。工作坊只寫在指令集 1 上，就在所有之後的核心上都能開。工作坊要同時在舊核心（0.7.x）上能開，就用 `hasattr(app, "call")` 判斷，沒有就走現在的 `app.page` 路線（舊的 `app` 方法在新核心上也還在，見 3.2）。

**問題 5：從零啟動。** `modules/` 空的：開機程式找不到核心模組，就從包裡隨附的那份複製一份（隨附包放在 `iPLoT/seed/`，唯讀，開機程式只讀不改）。有核心、沒有面板：`call("main")` 沒有提供者，核心模組開一個約 40 行的 tkinter 清單（列出模組、按一下就 `run`），一定還能開工作坊。這是唯一一個核心模組自己帶的畫面，而且只在沒有 `main` 提供者時出現。

### 3.5 安全：一條通用規則取代 `.origin`／`.unconfirmed`／`.hooks-ok`

任何模組都能宣告提供任何角色，所以工作坊裝來的模組可能宣告 `"app.trash"` 或 `"main"` 搶走系統功能。規則（核心模組裡唯一的政策，約 10 行）：

- 資料夾裡有 `.untrusted` 的模組：**它的 `PROVIDES` 不算數**，按它之前先 `call("app.confirm")` 問一次。
- 誰放 `.untrusted`：工作坊（它裝的東西）。核心不知道工作坊是誰，只認這個標記。
- 同一個角色有兩個提供者：`config.py` 的 `ROLES = {"main": "面板"}` 指定；沒指定就照掃描順序取第一個，並記一行「`main` 有兩個提供者，用了 X」。

## 5. 代價（說清楚，不打折）

1. **膨脹沒有消失，是搬家了。** 搬到「角色的約定」上：`menu` 傳什麼參數、`error` 回什麼。這些約定要有一份角色清單（每個角色：誰提供、誰使用、參數長怎樣、第幾版），不然會變成 Emacs 的 hook 那樣，誰掛了什麼沒人知道。要寫一個「角色檢視」模組，列出現在誰提供什麼（Emacs 的 `describe-function` 那種）。
2. **出錯比較難追。** 按一個鈕，經過面板 → `call("menu")` → 整理模組 → `call("app.trash")` → 作業系統。錯誤訊息要帶完整的轉接路徑。
3. **面板變成最重要的模組。** 面板壞了，使用者只看得到 3.4 的那個 40 行清單。面板改版要比現在更小心，要有自己的測試和行數上限。
4. **重寫的量大。** 2500 多個測試大部分綁在現在的 `Core`、`ui/` 結構上，估一半要改寫或搬進各模組。這不是一個週末的事，是三個版本。
5. **Mach 的教訓（微核心太慢）在這裡不太適用**：iPLoT 是人按鈕的速度，多幾層轉接無感。真正的風險是 L4／Mach 那一代學到的另一件事：微核心的難處在「介面定得好不好」，不在行數。指令集 1 定錯了，之後只加不減會很痛。所以指令集要先在一版裡試用，再凍結。
6. **只有工作坊自動更新的原則不變**，但核心變成模組之後，核心模組也不會自動更新，要按「更新」。面板、導覽列也一樣。這跟 William 的原則一致。

## 8. 0.8 的實作步驟

以 `origin/main` `6875078`（0.7.4）為起點，開分支 `kernel/0.8-roles`，PR 用草稿。每一步都要能從零啟動，舊模組照跑。

**#9 是什麼（Discussion #9，Angelina1114，11-16）：** 經「互通」另開的頁面，最上面那一列只有「主控面板」，沒有同一層、上一層、下一層；她要的是跟行事曆一樣。我讀程式的判斷（還沒跟她確認）：兩份導覽列（面板的 `ui/nav.py`、互通的 `nav.py`）都只畫主控面板、上一層、子模組，**都沒有同一層**；最上層的模組沒有上一層、多半也沒有子模組，所以只剩主控面板。行事曆有子模組，看起來才「對」。所以 0.8 的導覽列要補「同一層」，並讓兩條路用同一份。

1. **角色機制（核心，約 +40）**
   - `core/meta.py` 多讀頂層常數 `PROVIDES`（只認 `dict[str, str]` 的字面值，不執行）。
   - `Core.providers(role)`、`Core.call(role, *args)`、`Core.each(role, *args)`；執行一律走 `press`（快照、錯誤、排隊照舊）。
   - `App.__getattr__`：找不到的屬性轉成 `call("app.<名字>", ...)`。`app` 上現有的 18 個成員不動，`api_version` 4 → 5（只加不減）。
   - 模組可以用 `app.call(role, ...)`、`app.providers(role)`。
2. **先問一次（核心，約 +20）**
   - 有 `.origin` 的模組（工作坊裝來的），`PROVIDES` 先不算數；第一次掃到時 `call("app.confirm")` 問「『X』想提供：右鍵選單、頁面上方的導覽列……要允許嗎？」，答應了在資料夾放 `.roles-ok`（記下當時的 `PROVIDES` 內容）。
   - 工作坊覆蓋或更新那個模組時拿掉 `.roles-ok`；`PROVIDES` 跟記下的不一樣也要再問。
