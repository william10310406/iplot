## 2. 要改的（四件，各一個 commit）

### 2.1 `test_seed.py` 改成檢查不變的事

- `test_seeds_belong_to_the_research_assistant`：拿掉 `len(data) == 12`；每一個 `SEEDS` 裡的名字：`name`、`owner_id == RA_ID`、`owner`（跟現在一樣的帳號名）照舊核；鍵只能是 `tools/registry.py:4-5` 列的那些：種子的 `name`、`owner_id`、`owner`，機器人會寫的 `version`、`notes`、`issue`、`updated`，加上研究助理手動加的 `removed`、`warning`（README「下架、轉名字、警告」那幾件事不能讓 `test` 紅：紅了連下架的那一次都不部署）。另外核：`SEEDS` 以外、`owner_id` 是研究助理的，只能是 `PLANNED`（`tests/test_bundled_seeds.py`）或已經上傳過的（有 `version`）——防止有人手改出一筆來路不明的「研究助理的名字」。
- `test_received_starts_empty` 改名 `test_received_is_well_formed`：每個鍵是 issue 編號（ASCII 數字字串），值是 `{"name", "version", "owner_id", "at"}`（`at` 符合 `registry.AT` 的格式）；`name` 的 `registry.key()` 在 `registry.json` 裡；同一個 issue 編號不會出現兩次（JSON 本身不擋重複的鍵、`json.loads` 只留最後一個；是 `read_json_strict` 的 `_no_duplicates` 擋：讀得進來就沒有重複）。
- 其他 `test_seed.py` 的測試（保留三個名字、ghost、notice、拒收種子、研究助理可以傳）不動。
- 做好的樣子：`tests/test_seed.py` 全綠；全套是 `0 failed`（現在本機有隔壁 iPLoT 是 `2 failed, 557 passed`；runner 上沒有隔壁的 iPLoT：現在是 `2 failed, 553 passed, 4 skipped`，改完 `0 failed`、4 skipped）。

### 2.2 `ruff` 不檢查上傳進來的 `modules/`

- `pyproject.toml` 的 `[tool.ruff] extend-exclude` 加 `"./modules"`（現在是 `["tests/vendor"]`）：只排 repo 根目錄的 `modules/`；寫成 `"modules"` 的話 ruff 會排掉任何一層叫 `modules` 的資料夾（在暫存的複本試過：`tests/fixtures/modules/x.py` 的 F401 就被藏起來了）。
- 做好的樣子：在暫存的複本裡往 `modules/` 放一個故意不合 ruff 的檔（例如 `modules/x/x.py` 只有一行 `import os`），`ruff check .` 照樣 `All checks passed!`；同一個檔放到 `tests/` 底下就報 F401。（照第 3 節，M7.1 做的時候 main 上的互通已經是帶 `# noqa: I001` 的 0.2.0，不加 2.2 也是全過，所以要用這個故意的檔來看。）`tools/`、`tests/` 照舊全部檢查。
- `tests/test_workflows.py` 或新的小測試核一次：`pyproject.toml` 的 `extend-exclude` 有 `./modules`（免得以後有人拿掉，`test` job 就會被別人的上傳弄紅）。

### 2.3 「收模組」先跑測試，沒過就不收、不部署

在 `收模組.yml` 加一個 `test` job，照 `測試.yml` 的步驟（同一組 pin 住 sha 的 actions、Python 3.10＋3.12、`pip install -r requirements-dev.txt`、`ruff check .`、`python -m pytest -q`），`permissions: contents: read`、`timeout-minutes: 15`、`checkout` 的 `with:` 底下第一行 `ref: main`、第二行 `persist-credentials: false`（`test_receive_and_build_check_out_main` 核的是 `with:` 的下一行就是 `ref: main`）。**`requirements-dev.txt` 一起釘版本**：`pytest==9.1.1`、`ruff==0.17.1`（本機 `.venv` 現在的版本；現在只寫 `pytest`、`ruff`）——這個 job 變成部署的關卡之後，ruff 或 pytest 出新版就可能讓它無緣無故紅（iPLoT 的 D29：「工具一升版『乾淨』的意思就變了」）；`tests/test_workflows.py` 加一個測試核 `requirements-dev.txt` 每一行都是 `名字==版本`，升版另開 PR，讓「測試」先在 PR 上跑過。然後：

| job | 現在 | 改成 |
|---|---|---|
| `test` | 沒有 | 新的；第一個跑 |
| `receive` | 沒有 `needs` | `needs: test`（沒過就不碰任何 issue） |
| `build` | `needs: receive`、`if: ${{ !cancelled() }}` | `needs: [test, receive]`、`if: ${{ !cancelled() && needs.test.result == 'success' }}`——**receive 失敗照樣 build**（M7 的規矩：一份上傳出錯不能讓網站停在舊的；`test_build_and_deploy_survive_a_failed_receive` 釘著），**test 沒過就不 build** |
| `deploy` | `needs: build`、build 成功才部署 | 不變 |

- 為什麼 `receive` 也要等測試：`tools/` 壞了的話，它會拿壞的程式去改 `registry.json`、回覆別人的 issue、push 到 main。測試沒過時上傳就排著（issue 開著），下一次綠的那一次照 D104 一次處理全部。
- 為什麼不只是把「測試」也掛在 `push`：那樣是平行跑，擋不住同一次的部署。
- `test` 測的是 receive 動手之前的 main；receive 自己 push 的資料（新的上傳）不重跑測試——那是機器人照自己的規矩寫的，`build` 本來就會自己再驗一次（M7 Task 8）。用 `GITHUB_TOKEN` push 的 commit 不會再觸發 workflow（GitHub 的規則），所以不會繞圈。
- 測試裡要隔壁 iPLoT 的那四個（`test_bundled_seeds.py:25`、`test_rules_table.py:135`、`test_iplot_rules.py:170`、`test_build.py:131`，都用 `iplot_next_door`）在 runner 上會 skip，不擋。
- `tests/test_workflows.py` 跟著改（`:57-135` 的那幾個）：`test_build_and_deploy_survive_a_failed_receive`（`:102`）改核新的 `needs` 與 `if`；`test_receive_build_deploy_have_the_least_permissions`（`:76`，寫死 `{"receive", "build", "deploy"}`）加 `test` 與它的 `{"contents: read"}`；`test_receive_and_build_check_out_main`（`:93`，寫死 2 個 checkout）改成 3 個；新加 `test_tests_gate_receive_and_build`（`receive` 有 `needs: test`、`build` 的 `if` 有 `needs.test.result == 'success'`）；新加 `test_receive_runs_the_same_checks_as_the_pr`：「收模組」的 `test` job 與 `測試.yml` 的 `test` job，每一行 `uses:`、`run:` 一字不差、順序一樣，也都有 `persist-credentials: false`（兩份抄的步驟不會分岔）。`test_every_job_has_its_own_permissions_and_timeout`（`:67`）、`test_actions_are_github_own_and_pinned_to_a_sha`（`:84`）是掃全部的 job 與每一行 `uses:`，自動涵蓋新的 job。
- 做好的樣子：`tests/test_workflows.py` 的文字核對保證 `needs` 與 `if` 的接法（「收模組」只在 main 跑，沒辦法在 PR 上真的弄紅一次看它停；要親眼看的話，可以在一個自己的 fork 上故意讓一個測試紅，這次不做）。上線後的驗收：下一次 push 或排程的 run 有四個 job，`test` 綠，其他照常。

- `tools/iplot_rules.py:1` 的「iPLoT 的 repo 是 private，這裡 import 不到，只能抄。」改成「iPLoT 是另一個 repo（公開的），機器人的 checkout 裡沒有它、import 不到，只能抄。」
- iPLoT 0.6.0 合進 main 之後，`tests/test_bundled_seeds.py` 的 `PLANNED` 拿掉「回報與討論」（那時候 `git ls-files` 已經看得到它），同一個 commit 把它加進 `tests/test_seed.py` 的 `SEEDS`：2.1 的「`SEEDS` 以外的研究助理名字只能是 `PLANNED` 或有 `version`」不要靠它剛好已經從工作坊傳過。

1. M8 做完、0.6.0 發佈、互通 0.2.0 與「回報與討論」都上了工作坊之後才開始（研究助理定的順序）。

4. 上線後看一次 run：`test`、`receive`、`build`、`deploy` 四個都綠。

## 4. 風險

- **測試一紅，整個機器人就停**：別人的上傳要等研究助理修好才會被收（issue 開著、不會掉：D104 每次處理全部）。這是刻意選的「壞了就停」；代價是要有人看失敗通知。2.2 先把「別人的上傳弄紅 lint」這條路堵掉；2.1 把「資料變了測試就紅」堵掉。剩下會紅的是真的 `tools/` 壞了、手改的資料不合規矩（正好是要擋的），以及 PyPI 那一頭（`pip install` 連不上；版本沒釘的話還有 ruff、pytest 出新版）——所以 2.3 一起把 `requirements-dev.txt` 釘版本。
- **紅的時候研究助理自己的修改也不上線**：下架（`removed`）、警告（`warning`）、`notice.txt` 都要 build＋deploy 才到網站；`test` 紅時 build 跳過，網站停在上一次部署的樣子，下架的模組照樣列著、zip 照樣下載得到（`workflow_dispatch` 一樣被擋）。要緊急下架時，先讓 `test` 綠（修測試或資料），跟下架在同一個 push 一起上。
- 每一次 run（每小時一次、每開一個 issue 一次、每次 push 一次）多大約一分鐘；公開 repo 的 Actions 不收錢。
- `test` 的 checkout 與 `receive` 的 checkout 之間如果有人 push，`receive` 跑的是沒測過的那一版；`build` 也是 checkout 當下的 main，會把那一版一起部署。空檔就是 `test` 整個 job 的時間（setup-python 兩版、`pip install`、ruff、pytest，大約一分鐘），不是秒級。`concurrency` 只排「收模組」自己；那一次 push 自己觸發的 run 會排在後面再測一次，但擋不回已經部署的。可以接受；要更嚴就讓 `receive` 與 `build` 用 `test` 測過的那個 sha（`needs.test.outputs`），這次不做。
- 這一份沒有處理繁簡字的相似名字（`回報与討論` 現在擋不到：2026-10-24 對真的 `registry.py` 核過，機器人的「太像」不認繁簡）。那是另一題，影響也小（面板只認一字不差的 `modules/回報與討論`）。
