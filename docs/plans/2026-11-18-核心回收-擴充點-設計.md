## 3. 共同的規則：宣告不執行、照常 `press`

四個擴充點用同一套做法，核心只多兩件事：

**(a) 宣告。** 模組在 `iplot.py` 頂層寫常數宣告它要掛在哪裡。`core/meta.py` 已經用 `ast` 讀 `TITLE`、`ICON`，不執行模組；這次多讀幾個名字，一樣只認常數：

```python
MENU = {"改名…": "rename", "移到垃圾桶…": "remove"}   # 右鍵選單：顯示的字 → 函式名
ERROR_BUTTON = "回報這個問題"                           # 錯誤那一列的鈕；按了呼叫 on_error
ON_START = True                                          # 啟動時呼叫 on_start
```

**(b) 呼叫。** 掛上去的動作一律走現有的 `Core.press(info, handler, args)`。這條路本來就有：「作業系統」的動作（`Core.action`）和「回報這個問題」（`ui/web.py` 的 `report_error` 呼叫 `on_error`）都是這樣跑的。所以快照、錯誤顯示、排隊、`.unconfirmed` 的確認全部照舊，不需要新的執行方式。

核心要新增的只有一個函式，估 20 到 30 行：

```python
def hooks(self, name: str) -> list[ModuleInfo]:
    """宣告了 name 的模組，依掃描順序；有 .unconfirmed、或沒有被允許的（第 8 節）不算。"""
```

**(c) 安全。** 掛勾讓模組在使用者沒有按它的時候執行（啟動時），或出現在別的模組的選單上。工作坊的模組沒有經過審查（D100），所以規則是：**掛勾要使用者允許過才生效**，細節在第 8 節。

## 4. 擴充點一：啟動掛勾（`on_start`），回收 D156

**現在：** `main.py` 的 `bundle_news` 呼叫 `core/bundled.py` 的 `sync`，照 `.backup/download-<版本>.zip` 換隨附模組。核心因此要知道 `BUNDLED` 的名單、更新包的檔案配置、`bundled_hashes.json`。這全部是「更新」這個功能的事。

**改成：**
- 核心在面板開起來之後，對每個宣告 `ON_START = True` 的模組 `press(info, "on_start", quiet=True)` 一次。核心不知道它們做什麼。
- `core/bundled.py`、`core/bundled_hashes.json`、`tools/bundled_hashes.py` 整份搬到 `modules/更新/`（`bundled.py`、`hashes.json`）。「更新」宣告 `ON_START = True`，`on_start` 就是現在的 `sync`。
- `BUNDLED` 名單跟著搬進「更新」。它是「更新」的事：哪些模組隨核心發。

**順便打開的：** 自動啟動（`docs/05_使用紀錄.md` 行事曆待辦第 4 條：「iPLoT 啟動時自動打開行事曆」）、你方向裡的自動化流程，都是 `on_start` 的使用者，不用再改核心。原版 iPLoT 的 `AutoInvoke`（`autoFlag=["David"]`）就是這件事，現在做成模組可以宣告的東西。

**過渡（最麻煩的一點）：** 已經在用 0.7.x 的人，`modules/更新/` 是舊的、沒有 `on_start`。新的「更新」要怎麼送到他們手上？
- 做法：**0.8.0 的核心照舊帶著 `bundled.py`，最後一次用它把新的「更新」換上去**，同時新的「更新」宣告 `on_start`。之後的版本（0.8.1 或 0.9）才從核心拿掉 `bundled.py`。
- 代價：0.7.x 以前的人要先經過 0.8.0，不能直接跳到 0.9。「更新」看到版本跳太多要說一句。

**估計：** 核心 −104（`bundled.py`）、−8（`main.py` 的 `bundle_news`），＋8（啟動時呼叫掛勾）。

## 5. 擴充點二：右鍵選單（`MENU`），回收 D155

**現在：** 改名與移到垃圾桶的規則（隨附的不能動、工作坊的不能改名、撞名、不可攜的名字）寫在 `core/modify.py` 與 `Core.rename`、`Core.remove`。D155 的理由是「規則要在核心裡才擋得住網頁面板與備用面板兩條路」。

**改成：**

- 新模組「整理」（隨附）宣告「改名…」「移到垃圾桶…」。`modify.py` 的規則整份搬過去，用的是現有的 `app.ask`、`app.confirm`、`app.trash`、`app.rescan`。
- D155 的理由在新做法下依然成立：兩個面板都呼叫同一個模組的同一個函式，規則只有一份。
- `Core.memories.pop` 那一行（改名後把舊資料夾的記憶清掉）要一個公開的做法：`app.forget(info)`，或者核心在 `rescan` 時自己清掉已經不存在的資料夾。我傾向後者，不必加接口。

**順便打開的：** 你方向裡的「檔案整理」（例如「依日期歸檔」「移到某個工作情境」）以後就是在這裡加選單項目。HyperCard 用滑鼠把按鈕連到動作的那一層，第一步就是讓別人能往選單裡加東西。

**選單太長怎麼辦：** 項目多了要分組，宣告的模組名稱當小標題。這一版先不做，等真的超過 5 項再說。

**估計：** 核心 −42（`modify.py`）、−40（`Core.rename`／`remove`），＋10（`meta` 讀 `MENU`、面板列出來）；`ui/web.py` 的 Bridge 少 `rename`／`remove`，多一個 `menu(id, owner, handler)`。

## 6. 擴充點三：錯誤掛勾（`on_error`），回收 D110、D150

**現在：** 面板寫死 `REPORT_MODULE = "回報與討論"`。錯誤那一列有它才畫「回報這個問題」，按了呼叫它的 `on_error`。`ui/errlog.py` 自動問「要回報嗎？」，還照抄了「科學計算」認學生作業資料夾的方式（`student_homework`）。

**改成：**
- 宣告 `ERROR_BUTTON = "鈕上的字"`、加上 `def on_error(app, error)` 的模組，錯誤那一列各畫一顆鈕。按了就 `press(info, "on_error", (error,))`，跟現在一樣，只是不再認名字。
- 「這個錯誤不要問」也交給模組自己決定：宣告 `ERROR_SKIP` 的模組，或 `on_error` 回傳 `False`。「科學計算」自己宣告它的學生資料夾不問，`student_homework` 從 `ui/errlog.py` 搬回「科學計算」。
- **自動問「要回報嗎？」**（D150）：要不要保留，請你決定（第 11 節第 2 題）。保留的話，面板只對「宣告了 `ERROR_ASK = True` 的模組」問，問的字由模組給。要注意 `on_error` 自己出錯時不能再觸發一次，現在用 `error.module == REPORT_MODULE` 擋，要改成「正在執行的是錯誤掛勾就不再呼叫」。

**估計：** 核心幾乎不變；`ui/web.py`、`ui/tk.py`、`ui/errlog.py` 合計約 −40。

## 7. 擴充點四：頁面掛勾，回收 D153

**現在：** `ui/nav.py`、`ui/nav.js` 在每個 `app.page` 開出來的頁面最上面注入導覽列（主控面板、父層、子模組）。

**選項：**
- **A. 頁面掛勾**：宣告 `ON_PAGE = True` 的模組，在每一頁載入後提供一段 JS 注入。這是 D152 當時沒選的選項 C，沒選的理由現在還在：任何被允許的模組都能往別人的頁面注入 JS，而那一頁的 `pywebview.api` 摸得到別的模組的 Python 物件。
- **B. 導覽列留在 `ui/`，但改成通用的**：導覽列只用 `app.parent`、`app.children` 這種通用資料，不認得任何模組的名字（現在寫死「主控面板」）。這樣它不算為某個功能破的例，而是面板本身的長相。

**建議 B。** 這一版不做頁面掛勾。理由是風險最大、收益最小（只省 90 行，而且不在核心邏輯的上限裡）。等有第二個「想往別人頁面加東西」的需求出現再說。

## 7.5 擴充點五：執行方式（`PROCESS = "separate"`）

**問題（研究助理 2026-11-18 實際使用時碰到）：** 開著某個功能時回到主控面板，按別的模組都沒反應；把那個功能關掉，前面按過的才一次全部跳出來。行事曆沒有這個問題。

**原因（程式裡確認過）：**
- 網頁面板只有一條工作執行緒（`ui/web.py` 的 `WebPanel._work`），按下的每個模組都排進 `self._jobs`，一次只做一件。
- `app.page` 走到 `WebPanel.page`，停在 `done.wait()` 直到那個視窗關掉；這段時間工作執行緒被佔住，後面按的全在排隊。
- 行事曆繞開了：`open_or_focus` 用 `Popen` 經「互通」的 `run.py` 另開一個程序，自己馬上結束，面板空出來；頁面在那個程序裡開（`互通/popup.py` 的 `Popup.page`）。
- 在面板程序裡開頁面、所以會卡住面板的：工作坊、回報與討論、互通自己的狀態頁、車車。跑很久的模組也一樣。

**為什麼不改 `app.page` 讓它不等：** `app.page` 的約定是「視窗關掉才回來」（`docs/api.md`），既有模組在它後面寫的程式（例如行事曆關頁面後刪 `.pid`）會提早跑。改約定等於破壞所有頁面模組。

**改成：**
- 模組宣告 `PROCESS = "separate"`（`meta` 用 ast 讀，跟其他宣告一樣）。
- 某個模組宣告 `LAUNCHER = True` 並提供 `def on_launch(app, target)`：「互通」就是這個模組，`on_launch` 就是先修版裡的共用函式（另開程序；已經開著就叫到最前面）。
- `Core.press` 開頭多一個判斷：目標宣告了 `separate`、這個程序不是為它另開的、而且有 launcher，就改成 `press(launcher, "on_launch", (target,), quiet=True)`，馬上回來。沒有 launcher（沒裝互通）就照現在在面板裡跑，訊息區說一句。核心估 +10 行，不認得「互通」的名字。
- 判斷「這個程序就是為它另開的」用環境變數（先修版定的 `IPLOT_SEPARATE=<資料夾>`），寫進 `docs/api.md`，不是互通私下的約定。

**順便解決的：**
- `app.run(對方)` 呼叫一個 `separate` 的模組時，等於「叫了就走、不等它」。這是「模組互相呼叫」目前缺的第一件事（第 11 節第 6 題）。
- 導覽列（第 7 節選 B）的「跳」：現在是關掉這一頁再在面板裡跑目標。目標是 `separate` 的，就不用關掉這一頁，直接另開；「主控面板」那一格只把主控面板叫到前面，不關頁面。

**還沒解決、這一版不做：** 模組之間傳資料（叫對方時給它東西、拿回結果），與模組宣告「我能做哪些事」。另開程序之後只能用參數與檔案傳。

**代價：** 每另開一個就多一個 Python 程序、多花一次 pywebview 的啟動時間（沒量過，要量）；Dock 上會多一個「Python」圖示（行事曆換了自己的圖示，其他模組要自己換）；工作坊在另一個程序裡裝了模組，面板要重掃才看得到。

## 7.6 擴充點六：面板本身是模組

**起因（研究助理 2026-11-18）：** 面板一直在改，每改一次就是一次核心發佈。之後還會有一個「互通導覽列」模組：開著任何一個模組，都能從導覽列點到別處。

**先講清楚會省到什麼、不會省到什麼：**
- `CORE_LIMIT`（700，現在 695）只算 `core/`，面板在 `ui/`。所以把面板搬出去，**695 這個數字一行都不會少**。要讓 695 降下來，還是靠第 4 到 7.5 節。
- 會少的是種子：`ui/` 現在約 1046 行，加上 `main.py` 136 行，整顆種子約 1877 行。面板搬走以後約 800 行跟著離開，種子剩約 1080 行。
- 真正的好處是發佈方式變了：改面板就是改一個模組，經隨附同步（D156）或工作坊送出去，不用再發核心。11-01 以來動到 `ui/` 的 commit 有 11 個，每一個都是一次核心發佈。

**搬出去的（新的隨附模組，暫名 `modules/面板/`）：**

| 檔案 | 行數／上限 | 去向 |
|---|---|---|
| `ui/web.py`（WebPanel、工作執行緒、Bridge） | 237/240 | 面板模組 |
| `ui/app.js`、`index.html`、`style.css` | 274、31、128 | 面板模組 |
| `ui/nav.py`、`nav.js`（導覽列） | 36、33 | 導覽列模組（見下面「導覽列」） |
| `ui/errlog.py` 裡「要回報嗎」的那段 | 約 40/80 | 面板模組；寫錯誤紀錄的部分留下 |
| pywebview（`lib/`）的 import | | 只有面板模組 import，核心完全不碰 |

**留在核心的：**
- `View` 協定（`core/types.py`），這是面板模組要實作的介面，已經有了，不用新寫。
- **備用面板**：現在的 `ui/tk.py`（166/180）縮小，見下一段。
- `ui/install.py`（第一次啟動裝 pywebview）。之後也可以跟著面板模組走，但「從零啟動」要靠它，先留著。

**備用面板能做到多小：** 只要能救回來就好，不用好看。它只做四件事：
1. 列出所有模組，按一下就跑（照常 `press`）。
2. 一行字說明為什麼你在看備用面板，例如「面板模組『面板』開不起來：……」。
3. 兩個鈕：「換回隨附的面板」（從隨附的那一份重新複製，跟「更新」同一條路）、「這次先不用面板模組」（寫進 `config.py`，下次直接開備用面板）。
4. 訊息區（`log`），以及 `ask`、`confirm`。

右鍵改名、移到垃圾桶、錯誤那一列的鈕、建新模組的對話框都拿掉（那些是面板模組的事，或第 5 節「整理」模組的事）。估 166 → 約 80 行，`UI_BUDGETS` 的 tk 上限降到 90。用的是 Python 內建的 tkinter，不依賴 `lib/`，所以 pywebview 裝壞了它照樣開得起來。現在網頁面板開不起來時，`main.py` 的 `tk_or_exit` 已經會退到 tkinter，這裡只是把同一個退路用在「面板模組壞了」。

**為什麼面板模組壞掉不會整個打不開：** 因為選面板、載面板的那幾行在核心裡，而且它們只信一件事：面板模組的 `make_view` 有沒有在幾秒內回一個能用的 `View`。沒有、丟例外、或檔案根本不在，核心就開備用面板，並把錯誤寫進錯誤紀錄。所以最壞的情況是「醜一點，但東西都在」，不會是打不開。

**介面怎麼接：**
- 面板模組在 `iplot.py` 宣告 `PANEL = True`，提供 `def make_view(home, version, safe) -> View`。`meta` 用 ast 讀，跟其他宣告一樣。
- `config.py` 加一行 `PANEL = "面板"`（資料夾名，使用者可改成自己做的面板）。空字串表示一律用備用面板。
- `main.py` 依 `config.PANEL` 用檔案路徑載入那個模組、呼叫 `make_view`；拿到的 `View` 交給 `Core.attach`，再呼叫它的 `mainloop()`。這部分約 +15 行，寫在 `main.py`，不在 `core/`。
- 從工作坊裝來的面板（有 `.origin`）：面板摸得到所有模組，等於系統權限，所以不走第 8 節的「先問一次」，**只有使用者自己改 `config.py` 才會用它**。隨附的與自己寫的照常。
- 「從零啟動」：`modules/` 是空的，或面板模組不在，就直接開備用面板；備用面板上有「換回隨附的面板」，按下去隨附的面板就回來了。

**導覽列和面板模組的關係：** 兩個分開的模組，各自可以壞、各自可以換。
- 面板模組管「主控面板那一個視窗」：列模組、按下去、訊息區、錯誤。
- 導覽列模組（就是研究助理說的「互通導覽列」）管「每一頁最上面那一條」：在任何一個模組的頁面裡，點到別的模組、父層、子模組、主控面板。它的「點到別處」走 `press`，對另開程序的模組就經互通的 `separate.py` 另開（第 7.5 節）。
- 它們之間只靠核心給的通用資料（`app.parent`、`app.children`、模組清單），互相不 import。所以導覽列可以在面板模組壞掉時繼續用，反過來也一樣。
- 這一步順便把第 7 節選的 B 做完：導覽列搬出 `ui/`，核心裡不再寫死「主控面板」。注入導覽列仍需要一個「頁面開出來時」的接點，這是第 7 節 A 的那個風險，所以只開給一個模組：`config.py` 的 `NAV = "互通"`（或導覽列模組的名字），跟 `PANEL` 同一套規則，工作坊來的不自動生效。

**兩個都壞了怎麼救（由輕到重）：**
1. 面板壞、導覽列好：開著的頁面照樣能點到別處；主控面板那一格會開互通的救援頁。
2. 導覽列壞、面板好：頁面最上面沒有那一條，關掉頁面回面板就好；核心把導覽列的錯誤寫進錯誤紀錄，面板上看得到，可以按「回報這個問題」。
3. 兩個都壞：開互通的救援頁（見下面），上面有「換回隨附的面板」和「換回隨附的導覽列」。按下去，從隨附的那一份複製回來，重開就好了。互通也壞了，就是核心那約 30 行的最後一層。
4. 連備用面板都開不起來（例如 tkinter 也壞了）：`main.py --safe` 照現在的安全模式，只印出模組清單與錯誤；或者把 `config.py` 的 `PANEL` 改成空字串。這是最後一層，跟現在一樣，不新增程式。

**讓「互通」當救援入口（研究助理 2026-11-18 提的）：** 可以，而且比上面的備用面板更好，但核心還是要留一個很小的最後一層。
- 互通已經能做的：`run.py` 不經面板就能開任何一個模組（捷徑就是這樣開的），`separate.py` 能另開、能叫到最前面。再加一頁「所有模組」清單，加兩個鈕「換回隨附的面板」「換回隨附的導覽列」，它就是一個完整的救援面板，而且是模組，壞了可以改、可以從工作坊換。
- 所以分工改成：**面板模組壞了 → 核心開互通的救援頁**；互通也壞了才用核心自己的那一層。
- 互通扛不了的三種情況，就是核心還要留東西的理由：
  1. 從零啟動：`modules/` 是空的，互通不在。
  2. 互通自己壞了（改壞、或同步到一半）。
  3. pywebview 裝壞了：互通的頁面也是 pywebview 開的，跟面板一起倒。
- 核心最少留的：一個 tkinter 小視窗（只靠 Python 內建），一行字說哪裡壞了，三個鈕「換回隨附的面板與互通」「打開錯誤紀錄」「結束」。不列模組、不跑模組，估 30 行左右，取代上面那個約 80 行的備用面板；現在的 `ui/tk.py`（166 行）可以整個拿掉。
- 這樣分工的代價：互通變成系統的一部分，它的改版要跟面板一樣小心；第 7.5 節「沒有互通就照舊在面板裡開」的退路不受影響。

**會斷的地方（實作時要一起改）：**
- 互通 `separate.py` 用 `"ui.web" in sys.modules` 判斷是不是網頁面板；回報與討論的 `report.panel_kind()` 也是。面板搬走以後這兩個判斷就不準了。改成核心給 `app.panel`（「網頁」「tkinter」「面板外」，由面板的 `View` 自己報），兩個模組先讀 `app.panel`，讀不到再退回舊的判斷，這樣新舊核心都能跑。
- `tests/test_boundaries.py` 把 `app.js` 綁在 Bridge 的方法名上，要跟著搬進面板模組的測試。
- `UI_BUDGETS` 裡 web.py、app.js、index.html、style.css、nav.* 的上限，改成面板模組自己的上限（模組也有上限，不然只是把膨脹搬家）。

**代價：**
- 隨附模組多兩個（面板、導覽列），「更新」要同步它們；使用者改過的面板會被「更新」當成「改過的」，照 D156 的規則不蓋掉，但也就收不到修正。
- 面板的 bug 會以「模組錯誤」的樣子出現，第一次碰到的人會困惑；備用面板上那一行字要寫得清楚。
- 0.8.0 之前的人要經過一次「`ui/` 搬家」，這也要人工驗收。

## 8. 掛勾的允許規則

| 模組的來源 | 判斷 | 掛勾生效嗎 |
|---|---|---|
| 隨附的 | 「更新」的 `BUNDLED` 名單，而且沒有 `.origin` | 是 |
| 使用者自己新增的 | 沒有 `.origin`、沒有 `.unconfirmed` | 是：自己寫的程式，iPLoT 不替你擋 |
| 從工作坊裝來的 | 有 `.origin` | **先問一次**：第一次掃到它有宣告時，面板問「『X』想在啟動時執行／加進右鍵選單，要允許嗎？」，答應了在它的資料夾放 `.hooks-ok`。工作坊覆蓋或更新時拿掉 `.hooks-ok`，跟 `.unconfirmed` 同一套 |

問題：「核心判斷隨附」又會需要 `BUNDLED` 名單。解法是不判斷隨附：**只看 `.origin`**。隨附的模組沒有 `.origin`，跟自己新增的同等，本來就生效。這樣核心不認得任何名字。

`.hooks-ok` 和 `.unconfirmed` 是同一類東西（「這個資料夾的使用者決定」）。下一輪把兩個合成一個通用的標記檔，那時一起回收 D118 表上的 `.unconfirmed` 那一條。

## 9. 防膨脹：三條規則，其中兩條由 CI 擋

1. **上限只降不升。** `tests/test_budget.py` 加一個測試：`CORE_LIMIT` 不能高於上一個 tag 的值（讀 `git show <上一個 tag>:tests/test_budget.py`；CI 是淺 clone，要 `fetch-depth: 0` 或另外存一個 `core_limit.txt`）。真的要升，同一個 PR 必須回收 D118 表上至少一條例外，CHANGELOG 寫明。
2. **核心不認得任何模組的名字。** 仿照既有的「核心零作業系統程式碼」測試：掃 `core/`、`ui/`、`main.py`，`modules/` 底下任何資料夾的名字都不能以字串出現，`SYSTEM_MODULE` 是唯一的例外。以現在的程式，這條會擋到 `BUNDLED`、`REPORT_MODULE`、`nav.py` 的「主控面板」，正好就是這一版要回收的。
3. **改核心前先回答一題，寫進 D 決定：「第二個模組也會用到嗎？」** 會，就做成擴充點或通用接口。不會，就代表它是功能，應該做成模組，或做成某個擴充點的使用者。這一條靠人，不靠測試。
