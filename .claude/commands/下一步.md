替 iPLoT 排「接下來做什麼」。操作這個指令的是使用者的助理；訊息的收件人是使用者，使用者不會記得細節。**執行時不准問任何問題**：資訊不足的地方寫成「需要問他：…」，讓助理轉問。

使用時機：每天寫完日誌（`/日誌`）後排明天的事，或使用者不知道要做什麼的時候。這個指令只改 `docs/日誌/待辦.md`，不改程式碼，不切分支，不合併，不 push。

名詞：「使用者」是下指令的人（日誌裡的角色是「研究助理」）；「老闆」是另一個人（課程與需求的來源）。

## 0. 先弄清楚幾件事

```bash
TZ=Asia/Taipei date +%F            # <今天>
git worktree list --porcelain      # 第一筆是主工作區
```

`<日誌目錄>`：目前這個 worktree 有 `docs/日誌/待辦.md` 就用它；沒有的話，到 `git worktree list` 找有這個檔的 worktree（通常是分支 `docs/journal`，或已合進去的 `main`），讀寫與 commit 都用 `git -C <路徑>` 在那邊做。找不到就停下來，回覆「需要問他：要不要把 docs/journal 合進 main？」。

## 1. 讀

1. `<日誌目錄>/docs/日誌/待辦.md`（全部）。
2. `<日誌目錄>/docs/日誌/README.md` 頂端的兩週使用起始日（算今天是第幾天；「未設定」就是還沒開始）。
3. 最近 3 篇日誌：`ls <日誌目錄>/docs/日誌/2026-*.md | tail -3`，讀它們的「做了什麼」「留下的」「想要但做不到」。
4. 分支與工作樹狀態：

```bash
# 還沒合進 main 的分支，各比 main 多幾個 commit、最後一個 commit 是什麼時候
git for-each-ref refs/heads --format='%(refname:short)' | while read b; do
  n=$(git rev-list --count main.."$b")
  [ "$n" != 0 ] && echo "$b 比 main 多 $n 個，最後 $(git log -1 --format='%h %cd' --date=short "$b")"; done
# 每個 worktree 的分支與沒 commit 的變更（只列檔名）
git worktree list --porcelain | awk '/^worktree /{print $2}' | while read w; do
  echo "== $w"; git -C "$w" branch --show-current; git -C "$w" status --short; done
```

如果有分支寫了人工驗收清單（`docs/plans/` 底下檔名有「人工驗收」），打開讀，看已經勾了幾項（用 `git show <分支>:<路徑>`）。

## 2. 更新待辦.md

- **做完的打勾**：待辦裡的事，如果有 commit、合併、發佈、已勾完的驗收清單當證據，就把狀態改成「完成」並搬到「完成」那一節，寫上證據（短 hash）。沒有證據不准改成完成。
- **新冒出來的加進去**：最近 3 天日誌的「留下的」「想要但做不到」、分支狀態裡待辦沒有的事，加成新的一列（編號接續，不重用舊編號），每列都有：做什麼（白話）、為什麼、優先順序、狀態、預估。
- **兩週使用期間（起始日到起始日 +13 天）不排新功能**：新功能點子一律放到「兩週後才排」；只有修補、驗收、使用可以排進一到四節。起始日是「未設定」時，同樣先照這個規則排，並在訊息裡提醒起始日還沒定。
- 狀態只有四種：未開始／進行中／等我驗收／完成。更新頁首「最後更新」的日期。
- 不要刪掉任何一列；不做了的事改寫「不做了：原因」並搬到「完成」那一節的最後。

## 3. 挑出接下來最該做的 1–3 件事

挑的順序：

1. 擋住別的事的（例如：驗收沒按完，就不能合併、不能發版、不能開始兩週使用）。
2. 風險高的（公開、個資、使用者的資料）。
3. 花時間少、做完就能解開別的事的。
4. 起始日已經過了，只能選修補、驗收、使用。

一次最多 3 件。每件事分成兩種之一：

### A. 要在 Claude Code 做的

用下面的格式寫（這是要傳給使用者的訊息的一部分）：

```
【事情】一句話說要做什麼。
【為什麼現在做】一句話。
【大概多久】Claude Code 約 X；使用者要動手的部分約 Y（沒有就寫「不用」）。
【怎麼開】
- 模型：…
- 投入程度：…
- Ultracode：開／不開
- 提示詞（整段可以直接貼）：
  （完整提示詞，見下）
```

**模型、投入程度、Ultracode 的原則：能用小的就不用大的，不浪費額度。**

- 模型：純機械的（整理文件格式、搬檔、跑指令、改措辭）用 `claude-haiku-5-5`；一般的程式修補、寫測試、寫文件用 `claude-sonnet-5-5`；要做設計取捨、碰安全或隱私（遮蔽、風險提示）、跨很多檔案的重構才用 `claude-opus-5-5`；`claude-fable-5-1` 只留給前面都處理不了的最難的事，而且要在訊息裡寫明為什麼要用它。
- 投入程度：機械的 low；一般的 medium；要仔細推理的 high；xhigh、max 只在 high 做不好之後才用。
- Ultracode：預設**不開**。只有「有很多件互相獨立的子任務，而且要交叉檢查」（例如全專案審查、批次改很多模組）才建議開，並說明為什麼；一般修補、驗收、寫文件都不開。
- 提示詞要能脫離這段對話單獨用：寫清楚在哪個分支（或要開新分支）、要改哪些檔案或看哪些文件（用 repo 內的相對路徑）、做完的標準（跑哪些測試、要全綠）、**不准做什麼**（例如不合進 main、不 push、不發版）、做完要回報什麼。一律要求先寫失敗的測試再修（紅燈再綠燈），並且每個 commit 都要測試全綠、`ruff` 乾淨。提示詞裡不放本機路徑；需要路徑時寫「repo 根目錄」。

### B. 使用者要自己用滑鼠做的（例如人工驗收）

寫成可以照著做的步驟：

```
【事情】一句話。
【為什麼現在做】一句話。
【大概多久】X 分鐘。
【步驟】
1. 先做什麼（要開哪個分支、哪個程式、哪個畫面）
2. 按哪裡、看到什麼才算過
3. 沒過的時候要記什麼（哪一項、看到什麼）
【做完回報】只要回報：全部通過，或「第 N 項沒過：看到…」。
```

步驟從驗收清單抄，不要自己改編；清單太長就只挑這一輪要做的那幾項，說明為什麼挑它們。

### 需要使用者決定的事

如果最該做的事卡在使用者的決定（例如待辦裡寫著「需要問他」），不要替他決定：把它寫成「需要問他：…」，附上選項與你的建議（一句話），然後再挑一件不用等他決定的事。

## 4. 輸出給助理的訊息

最後的回覆**就是**要傳給使用者的訊息，用白話、不要術語堆疊，結構固定：

```
今天是 YYYY-MM-DD（兩週使用第 N 天／還沒開始）。接下來建議做這幾件事：

1. （事情 A 或 B 的格式）
2. …

需要問他：
- …（沒有就整段省略）

待辦.md 已更新並 commit：完成 X 項、新增 Y 項、現在還有 Z 項沒完成。
```

訊息裡不放本機路徑、不放學生資料、不放對話原文。

## 5. Commit

只 commit `待辦.md`：

```bash
git add docs/日誌/待辦.md
git commit -m "待辦：<今天>" -- docs/日誌/待辦.md
```

訊息第一行是「待辦：YYYY-MM-DD」；環境要求的結尾行（例如 Co-Authored-By）照加。在 `<日誌目錄>` 目前的分支上 commit，不 push。待辦沒有任何變動就不 commit，訊息裡寫「待辦沒有變動」。
